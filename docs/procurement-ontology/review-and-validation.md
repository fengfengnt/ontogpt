## 4. 发布原子性必须怎样验证

测试必须在实际采用的 Fuseki/TDB2、HTTP 更新方式和固定镜像上运行。至少包含成功发布、并发读者、两个同时写入者、版本条件未命中、写入中断或可控事务失败，以及重启后的结果核对。

只发送一个语法错误的 SPARQL 请求不足以证明“写入部分内容后仍会回滚”。测试需要证明目标快照和指针不会半提交。条件更新返回 HTTP 成功时，也要区分“目标发布确实发生”和“条件不满足，未发生任何更新”。

验收只接受旧完整版本或新完整版本；半图、指向不存在快照的指针、两个同基础版写入均被当作成功、失败后残留可见新版，任一出现均不能启用正式发布。

## 5. 证据层次与完成判据

| 证据层次 | 能说明什么 | 不能代替什么 |
| --- | --- | --- |
| 文档/静态代码 | 规定了架构、字段和规则 | 实际服务和数据行为。 |
| 单元测试/替身模型 | 指定分支和校验逻辑符合预期 | 真实模型效果或 Fuseki 事务。 |
| 真实 Fuseki 集成测试 | 图存储、事务、并发和恢复行为 | 浏览器或模型抽取质量。 |
| 服务健康/API | 服务可访问、指定接口返回预期 | 用户实际界面操作。 |
| 真实模型运行 | 指定资料、模型和版本下产生的候选 | 候选事实真实性或人工审核。 |
| 浏览器操作与视觉检查 | 当前界面的入口、交互和可读性 | 未运行的 API/MCP 反例。 |
| 人工业务核对 | 样本条目、范围和回答符合业务理解 | 所有未知输入都正确。 |

最终需同时满足需求矩阵的必要检查，记录运行版本和实际通过结果。缺少模型连接、浏览器证据或恢复验证时，对应项保持“未验证”，不得把文档完成、构建通过或 HTTP 200 写成 MVP 全部完成。
