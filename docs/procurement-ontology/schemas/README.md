两家公司使用各自文档、YAML 和生成模块，即使某些字段内容相同也不合并为一个业务 schema。通用来源、审核、权限和发布模型由服务维护；企业 YAML 负责描述业务提取形状和提取提示。

## 提取结果与治理元数据

模型可输出条目标签、陈述、业务属性、关系、适用范围和原文摘录。企业 ID、品类 ID、来源修订 ID、schema 版本、哈希、正式条目 ID、操作者、模拟标记及启用指针由服务端附加或验证，不能由模型自由决定。

两套 schema 都给每条候选提供 `evidence_quote`，必要时提出位置提示；服务重新在原文中定位。模型给出的片段、位置或关系无法核对时，保留待补证建议。业务范围至少区分设备类型、项目和阶段；“来源没有说明”与“没有范围限制”不能视作同一含义。

每套 schema 的关系提取使用局部临时引用或标签，服务只在本次企业候选集合及允许的本企业已有条目中解析。无法解析的端点不能静默创建成事实；关系类型不在本版规范中时转为 schema 缺口。

两套根类另有 `unmapped_suggestions[]`，保留有原文依据但当前字段/关系无法表达的信息及建议名称，供缺口流程消费。该字段不使草案自动启用。

## 版本及评审规则

`v1` 的 YAML/Python 目标目录见 [目录结构](../directory-structure.md)。初始 schema 先依据文档实现，再做 LinkML 解析、生成、导入及甲乙样本提取测试；不能用手工整理好的候选替代实际模型提取验收。

新增字段或关系走新版本目录和独立 Git 审阅。生成的 Python 由 LinkML 输出，不能由模型直接编写或人工修补后当成确定性生成物。删除、重命名及类型变化不在自动修订范围。

评审同时核对三层内容：schema 能否表达、原文是否支持、业务人员是否确认。通过结构校验只表示输出符合字段要求，不证明材料陈述真实，也不证明某条采购条件应当成为企业永久默认规则。

## 自动草案的实施边界

提取运行中的 `unmapped_suggestions` 只有在原文片段已核对时才触发草案。服务把片段交给模型，模型只能返回受约束的新增字段/关系 JSON，不能提供路径、命令或 Python。`detect_gap` 再检查企业、原文、已有字段、允许的业务类和原始摘要。

草案生成器核对独立 Git 工作树属于同一工程、分支以 `codex/schema-draft/` 开头、基础文件摘要未变，随后只写 `vN+1` 目录。LinkML 生成 Python 并做语法检查；导入/业务回归在不含业务凭据的测试环境执行。模型无法更改生成代码。生成失败保留待审目录和失败状态，部署人员检查后处理，不自动删除工作树。

管理页面显示草案状态、来源和 YAML 差异。草案分支需要人工 Git 审阅、生成一致性及回归测试；部署人员将新 YAML/Python 和对应摘要注册项部署完成后，企业审核人再执行 `activate-schema <公司> <二级品类> <版本>`。草案生成器没有更新注册表或 SQLite 的权限入口，部署完成也不会自动启用。
