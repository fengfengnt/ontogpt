# 采购企业与供应商本体知识服务：第一阶段设计

状态：用户已书面认可设计；不表示功能已实现。

## 目标与验收边界

在本仓库新增独立的采购本体知识服务，不修改现有 OntoGPT Web 演示应用。服务将一家甲方、一家乙方的资料变为可溯源的候选知识，经企业人员确认、管理员发布后，通过业务 JSON API 和 MCP Tools 授权读取。首个数据样本是[模拟笔记本采购案例](../../../tests/fixtures/procurement/laptop-purchase-case.md)提炼出的[知识包候选](../../procurement-ontology/laptop-knowledge-pack-candidate-v0.md)。

本阶段的成功标准是：甲方 Agent 能查到“电脑(台式机/笔记本)”二级品类知识包中适用于办公笔记本的采集字段、条件模板和来源；乙方 Agent 能查到本企业已发布能力与事实；未发布、过期或未授权内容不会混入普通查询。服务不回答某乙方是否满足本次采购、不给入围建议，也不保存采购业务状态。后续用简单 LangChain/LangGraph Agent 验证回答是否忠实引用这些本体内容，属于下一项工作。

## 技术与部署边界

采用以下单一方案：`services/procurement_ontology/` 为独立 Python 服务；FastAPI 提供业务 JSON API 和最小治理页面；Apache Jena Fuseki/TDB2 是本体、候选、来源和版本的权威存储；MCP 服务仅调用相同的读取逻辑。OntoGPT 可作为候选抽取组件，但其现有提取流程要求模板；首次无业务 schema 时先用五种通用候选结构的抽取适配器，不能把未经验证的 OntoGPT 输出视为企业事实。外部 Agent 不直连 Fuseki。

不采用两种捷径：扩展已有 Web 演示应用会把租户、审核与发布状态压进提取界面；先用普通 JSON 文件作权威库会绕过已经确定的 RDF 版本布局，后续还要迁移。试点机器有 Python/uv 和 Java，当前 PowerShell 未检测到 Docker 命令；本地联调可直接启动 Fuseki，不依赖 Docker。

账户与服务身份由本服务管理。系统管理员创建企业和企业管理员；企业管理员授权资料维护、候选确认、发布和读取权限。账户、密码哈希及服务令牌元数据放在本服务的 SQLite 管理库中，企业本体内容放在该企业的 TDB2 数据集。服务端从认证身份确定企业和角色，拒绝用请求体自报的企业 ID 越权读写。Fuseki 只开放给本服务的受控网络地址。

## 核心数据模型

| 对象 | 最小内容与关系 |
| --- | --- |
| 企业分类树 | 固定三级：`采购负责类 → 一级品类 → 二级品类`，节点有稳定 ID、名称、定义及唯一父节点。甲乙方各有自己的树与发布版本。 |
| `KnowledgePackage` | 属于甲方一条已发布二级品类节点；同一企业和节点在一个本体版本中至多一个当前知识包。知识包由可单独引用的条目构成。 |
| 知识包条目 | `CollectionField`、`SupplierConditionTemplate`、说明性知识分别有稳定 ID、定义、适用设备类型/阶段、来源引用及版本。判定说明可作为文本知识保存，但本阶段不执行判断。 |
| 乙方能力与事实 | 能力独立于品类节点，引用乙方自己的二级品类；事实逐条记录主体、关系、值、品牌/地域/项目等范围、有效期和来源。是否可供采购匹配由乙方发布时明确确认。 |
| 来源修订与片段 | 记录原文、提交人/时间或文件名、修订号；片段有位置和摘录。同一事实可引用多份独立来源。模拟案例须标为模拟，不得冒充真实企业事实。 |
| 候选与发布版本 | LLM 提议或图上编辑先进入企业待审队列；人工采纳/拒绝并处理冲突后由企业管理员发布不可改完整快照。分类树与业务本体分别版本化，先发布新树节点，再发布引用它的知识包或能力。 |

“笔记本电脑”是现有二级品类`电脑(台式机/笔记本)`中的设备类型，**不增加第四层分类**。首个知识包的案例条目初始只适用于`设备类型=办公笔记本`；台式机专属知识待独立资料补充。案例中的 100 台、16GB、500 万元等是本次取值，不是所有采购的默认约束。常识归纳没有企业原文时只列建议；企业人员补充明确表述作为新来源后，才可形成待确认候选并发布。

## 写入、确认与发布

1. 资料维护者提交自然语言或 Markdown。服务保存不可变的来源修订，按来源位置生成候选；模型不能给出可在原文定位的支持片段时只产生`MODEL_SUGGESTION`，不能进入事实候选。
2. 候选按分类树节点、知识包条目、职位/流程定义、约束、乙方能力或事实归类。每条显示原文片段、适用范围、有效期、依赖与潜在冲突。审核人可逐项或批量采纳/拒绝；图上编辑已发布内容会生成修订进入当前批次。
3. 每家企业同时最多有一个待发布业务本体批次和一个待发布分类树批次，两者独立。发布前检查引用闭包、来源、树的唯一父节点、同一生效期冲突和基础 RDF 结构。新分类节点先独立发布，后发布引用它的业务本体。
4. 企业管理员发布时，在该企业 TDB2 数据集的一次事务中生成新的完整版本图、更新当前指针和读取视图。失败保留旧版；历史版本与来源不可改。批次审核状态和操作者写入审计记录。

试点初始数据先作为**模拟候选**导入演示企业，管理员显式确认后才能出现在只读接口；不能在部署时直接标记为真实企业已确认知识。后续真实资料走同一流程。

## 授权查询与 MCP

第一阶段只给 Agent 两项能力：`search_ontology_items`按自然语言或关键词返回有权可见的条目 ID、类型、摘要、三级路径与实际版本；`get_ontology_item`按 ID 返回条目详情、直接相邻的一跳关系摘要、适用范围、有效期以及获授权的来源片段。搜索最多返回十条、每条最多三跳的真实关系路径；路径相关性不等于条件已满足。两项 MCP Tools 包装同一服务方法，权限过滤先于检索和结果计数。

普通查询只读最新已发布的企业本体和分类树，不接受任意旧版搜索。响应回显实际版本；搜索后发生发布时，带旧观察版本的详情读取给出版本变化提示。未授权的跨企业 ID 不可借`get`直接读取，来源正文和私有事实也不能经关联路径泄漏。完整原文只在本企业资料治理界面按资料权限查看。

管理操作包括：建企业/账户、提交来源、查看候选、采纳/拒绝与图上修订、检查发布差异、发布分类树或本体版本、查看来源与审计。管理操作不通过普通 Agent MCP Tools 暴露。

## 错误处理与可靠性

- 抽取失败保留来源修订及错误，绝不生成已发布事实；可在同一来源修订上重试提取而不重复创建同义候选。
- 引用未发布节点、来源缺失或生效期冲突时阻止发布，返回具体条目和原因。发布事务失败时当前版本不变。
- 未授权访问不返回条目内容或来源片段；租户解析和角色检查均在服务端进行。
- 提供企业数据集备份与恢复步骤；试点验收实际重启服务并恢复备份，核对当前指针、历史快照、候选批次与来源引用一致。

## 验证顺序

1. 用模拟案例夹具生成甲方知识包候选，核对条目来源行号及模拟标记；无来源的常识建议不能自动成为事实。
2. 管理员确认并发布三级树和知识包。发布前查询看不到候选；发布后搜索“电脑采购”并按 ID 读出笔记本适用字段、条件模板和引用；不会把案例数值显示为通用默认硬约束。
3. 导入一份最小乙方资料，发布能力和范围事实；乙方可读自身内容，甲方在未获披露授权时不可读其私有事实。
4. 修改条目后验证旧版在下次发布前仍被读取；发布成功后读到新版，旧快照和来源可供审计；发布失败无半成品。
5. 经 API 和 MCP 分别调用同一查询，校验结果与权限一致；重启及恢复后重复关键查询。

本阶段不实现采购草案分析、跨企业品类等价判断、供应条件核验、入围结论、正式业务写入、LangChain/LangGraph Agent、RDF/OWL 文件交换或开放 SPARQL。

技术依据：[Apache Jena TDB2 与 Fuseki](https://jena.apache.org/documentation/tdb2/tdb2_fuseki.html)、[Apache Jena 事务](https://jena.apache.org/documentation/tdb/tdb_transactions.html)、[MCP 官方 Python SDK](https://github.com/modelcontextprotocol/python-sdk)。
