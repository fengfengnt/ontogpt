# 采购本体知识服务 MVP 详细设计

状态：待用户审核书面设计。本文取代 [2026-10-16 第一阶段设计](2026-10-16-procurement-ontology-knowledge-service-design.md)；旧实施计划尚未按本文修订，不得据此实施。

## 目标与范围

在 OntoGPT 仓库内新增独立的采购本体知识服务，以二级品类 `电脑(台式机/笔记本)` 完成甲乙双方各一条端到端样例：从各自材料中由模型自动提取候选，逐条核对来源并由人审核，在浏览器画布上编辑企业业务本体的条目与关系，将其发布为不可变版本，再由本企业用户经 JSON API、MCP 和一个简单 LangGraph Agent 查询。Agent 的测试页面须显示答案及实际引用的知识条目。

MVP 试点企业为 `test_buyer1` 和 `test_supplier1`。两家企业的原文、自然语言表达、提取 schema、分类树、业务本体和 Fuseki 数据集彼此独立。乙方样本来自一份模拟的上海联畅科技有限公司（联想代理商）中标方视角案例；甲方样本同样为模拟案例。样本中出现的企业、报价、成本、过程和结果均是模拟资料中的陈述，不得宣称为经核实的真实企业事实。

分类层级固定为 `采购负责类 → 一级品类 → 二级品类`；`行业`另行定义。平台维护通用本体和一棵通用三级分类树；每新建一家企业，就以两者当时已发布的版本初始化该企业独立的本体和三级树实例，并记录来源版本。办公笔记本、台式机是二级品类内部的设备类型，不增加第四层。案例中的数量、价格和参数属于具体项目，不成为整个品类的默认硬约束。

本服务只管理知识提取、审核、发布与读取。外部业务系统保存采购流程记录；MVP 不做跨企业知识合并、甲乙匹配、资格判定、入围建议、合同管理、公开 SPARQL 或通用 Agent 平台。`media` 是用户举例，MVP 不创建该品类的 schema。

## 技术架构与职责

| 单元 | 职责与边界 |
| --- | --- |
| OntoGPT 提取适配器 | 按已启用的企业/品类 schema 调用模型提取；输出候选，不直接写已发布图。 |
| Schema 仓库与注册表 | Git 管理各企业版本化 LinkML YAML、确定性生成的 Python 和 `schema_registry.yaml`；注册表描述可部署版本、根类及文件校验值。 |
| SQLite 管理库 | 保存账户与服务身份、每企业每二级品类的启用 schema 指针，以及激活审计；不充当业务本体权威库。 |
| Fuseki/TDB2 | 平台通用本体与通用三级树使用独立的平台数据集；每企业独立数据集保存本企业来源修订、候选、审核记录、三级树实例与业务本体的不可变发布版本，以及各自的当前发布指针。 |
| 采购本体服务 | `services/procurement_ontology/` 中的独立 Python 服务；统一实现身份检查、候选审核、发布和只读查询。FastAPI 提供管理及业务 JSON API，MCP 只适配同一查询服务。 |
| 可视化管理前端 | 企业工作区的画布只编辑本企业业务本体条目和关系；三级树在单独的树形菜单增删改。平台工作区只管理通用本体和通用三级树。所有写入经管理 API 审核与发布，前端不是权威存储。 |
| LangGraph 演示 Agent | 以服务端固定的 `test_buyer1 / 电脑(台式机/笔记本)` 范围调用只读搜索与详情，使用已发布条目回答问题。测试页是该 Agent 的入口。 |

实现依赖以本仓库已有的 Python、LinkML、Pydantic、FastAPI 能力为基础；新增 LangGraph 和 MCP Python SDK 仅用于已确定的 Agent/MCP 入口。演示 Agent 与提取器通过服务配置取得模型连接信息，不在仓库、页面或提示词中硬编码密钥。

本项目从 MVP 起使用 `React + TypeScript + Vite` 建独立前端，目录为 `frontend/procurement-ontology/`，并使用 Cytoscape.js 绘制企业业务本体画布。企业工作区提供资料提交、候选审核、本体画布、三级树菜单、发布和 Agent 问答；平台工作区只提供通用本体和通用三级树的管理入口。浏览器通过 `fetch` 调 FastAPI JSON API。先用原生表单和普通 CSS，不引入通用状态库或大型组件库。生产构建由本服务以同源路径提供，开发环境经 Vite 代理访问 API。浏览器只持有登录会话，不持有 Fuseki 或服务间凭证。

初始界面采用 [Claude `DESIGN.md`](https://github.com/VoltAgent/awesome-design-md/blob/main/design-md/claude/DESIGN.md) 所分析的暖色纸面、克制的珊瑚色强调与清晰排版；这些是视觉参考，不使用 Claude 标志或未获授权的专有字体。项目自己的 `frontend/procurement-ontology/DESIGN.md` 记录实际采用的界面规则；`src/styles/tokens.css` 用语义 CSS 变量集中定义背景、文字、强调色、状态色、字体、间距和圆角。表单、面板及 Cytoscape 节点/边样式都从这些变量取值，不在各页面散落品牌色。

以后改为 [MiniMax `DESIGN.md`](https://github.com/VoltAgent/awesome-design-md/blob/main/design-md/minimax/DESIGN.md) 一类风格时，先更新项目 `DESIGN.md` 与 `tokens.css`，再做浏览器视觉与可读性检查。颜色、字体、圆角的替换较集中；如果新风格要求不同的信息密度、导航或组件布局，仍须修改对应组件，不能只替换一份 Markdown 就完成改版。MVP 不做用户可见的实时主题切换。

```text
src/ontogpt/templates/company/

  test_buyer1/computer/v1/
    test_buyer1_computer.yaml
    test_buyer1_computer.py
  test_supplier1/computer/v1/
    test_supplier1_computer.yaml
    test_supplier1_computer.py
docs/procurement-ontology/schemas/
  test_buyer1/computer/v1.md
  test_supplier1/computer/v1.md
services/procurement_ontology/
  schema_registry.yaml              # Git 管理的可部署版本清单
frontend/procurement-ontology/      # React/TypeScript/Vite 管理与问答页面
  DESIGN.md                         # 项目实际采用的界面规则
  src/styles/tokens.css             # 页面与画布共用的语义样式变量
deploy/fuseki/                       # 本项目独立的 Docker 配置
```

后续 `v2` 与 `v1` 并存，不能覆盖已用于抽取的版本。两家公司即使字段相同，也各有独立 YAML、Python 和设计文档；共享的只是加载、校验、审核、发布和查询机制。`schema_registry.yaml` 以企业 ID、品类 ID 和版本定位相对路径、根类及产物 SHA-256，不表示当前启用版本。运行中的服务不根据目录扫描结果自行选择 schema。

现有 `get_template_details` 对自定义 YAML 会复制到根模板目录并在运行时生成 Python；普通 `get_template_path` 也只定位根目录。企业 schema 需要独立的按注册表路径加载入口，部署前生成 Python，并验证嵌套目录中的 LinkML 导入。现有 OntoGPT Web 演示模板选择器不枚举或暴露企业模板。

## 两套业务 schema 的初始内容

甲方 schema 围绕二级品类知识包：资料采集字段与建议提问、资格/技术/商务条件模板、条件适用的采购阶段与设备类型、术语定义、品类流程说明。条件模板是可引用的知识，不由本服务执行条件判定。项目中的 `100 台`、具体配置和预算，只能作为带项目范围的示例值。

乙方 schema 围绕本企业供应知识：企业事实及资质陈述、品牌授权与产品供给能力、地域/交付/售后能力、项目范围的能力证据、内部成本和报价策略。模拟案例中的内部成本及底价可以存储、审核、发布，之后由该乙方企业内获准读取本体的用户直接查询；不得传播给甲方。项目专项授权、成本和报价策略均须带项目范围和来源，不能泛化为永久企业能力。两套 schema 文档分别给出字段定义、关系、适用范围和原文示例。

## 来源、候选、审核与缺口发现

1. 企业资料维护者提交自然语言或 Markdown。服务保存来源修订、提交身份、时间、内容校验值与 `simulated` 标记；同一修订可重试抽取。
2. 抽取开始时，从 SQLite 读取企业和二级品类的启用 schema，固定版本和文件校验值，记录在本次 `ExtractionRun`。中途切换启用指针不改变运行中的任务。
3. 模型按该企业 YAML 的字段及关系生成候选。服务核对每条候选声称的摘录是否可在该来源修订定位，并记录位置、摘录、来源 ID、适用范围和候选类型。无可定位支持的输出只能保留为待补证建议，不能作为事实候选发布。
4. 审核人查看原文、模型候选、范围、模拟标记和冲突，逐项采纳、修订或拒绝。修订须保留原候选与审核轨迹；已发布内容的修改只能进入新批次。企业管理员发布通过验证的完整新版本。
5. 资料或用户自然语言中出现当前 schema 无法表达的新字段/关系时，系统记录缺口和原文依据，自动起草**仅增加字段或关系**的 YAML 修订，并用 LinkML 生成 Python；草案不被运行时导入或启用。删除、重命名、改变类型和跨企业关系不由 MVP 自动修订。

Schema 草案放在待审 Git 分支的新版本目录，生成的 Python 随 YAML 一起审阅；运行时只加载注册表中已部署且被 SQLite 指针选中的版本。审阅展示 YAML 差异、来源理由、生成结果、前后样本提取及回归测试。审核通过并部署版本文件与注册表后，才允许通过管理命令显式启用。模型不得直接编写可执行 Python，也不得自动修改启用指针。

## 启用 schema 与发布本体是两条版本线

`activate-schema <公司> <二级品类> <版本>` 由目标企业具备 schema 管理权限的审核人执行，初始 `v1` 也走该命令。命令使用管理账户的凭证调用服务端激活操作；服务端验证目标公司与账户绑定企业一致，并从账户取得操作者 ID，不接受自报的审计身份，也不在日志中记录凭证。服务端检查版本已在部署的注册表登记、YAML/Python 存在且校验值匹配、LinkML 根类可解析、生成模块可导入。完整 Git 审阅与测试是部署前步骤，命令不伪称能重新证明这些历史步骤。检查成功后，在一个 SQLite 事务内更新启用指针并写入操作者、时间、旧版、新版审计；失败则两项都不提交。新指针只影响此后开始的抽取。

本体发布指针独立保存在对应企业的 Fuseki 数据集中。来源、候选与已发布版本分开；普通查询只读当前已发布的企业三级树和业务本体完整快照。企业三级树与业务本体分别版本化，引用新分类节点的本体必须在该节点发布后才能发布。平台通用树及通用本体也各自版本化，其发布不直接修改企业数据集。历史快照不可改，查询结果回显实际本体版本与来源。发布时计划在同一 TDB2 写事务中完成新快照与当前指针切换；**必须在真实 Fuseki/TDB2 上验证查询的原子可见性和失败回滚，验证通过前不启用发布功能**。若所选 HTTP 更新方式达不到要求，应调整发布实现并重新验证，不以设计推断代替实测。

搜索后发生发布时，详情请求携带搜索所见的版本；若当前版本已变化，返回明确的版本变化结果，避免把两版条目混合解释。抽取失败只留下来源修订及失败状态；重试不得重复发布或复制同义候选。发布校验至少检查来源、引用闭包、企业归属、唯一父节点、范围/有效期和同一版本内的冲突。

## 企业隔离与查询

服务端把账号分为平台管理员和企业账号，企业账号绑定唯一企业 ID。企业管理员的工作区只展示本企业、本企业业务本体和本企业三级树；其管理 API 只能写入该企业数据集。平台管理员的工作区只展示平台通用本体和通用三级树；其编辑 API 只能写入平台数据集，不能修改企业业务本体或企业三级树。MVP 不为平台管理员开放企业业务知识的读取入口；企业开通时由服务执行通用本体和通用树实例化，不借用平台管理员身份直接编辑企业数据。

认证在服务端解析账号的数据域，企业账号据此选择唯一企业数据集；请求体、模型输出和浏览器参数不能替换该身份。甲方只查询甲方自己的本体，乙方只查询乙方自己的本体，不做跨企业关联查询。企业内获准读取本体的用户可读取该企业全部已发布知识，包括内部成本和报价策略。管理操作仍需各自权限；岗位/角色细分的**知识条目级**访问逻辑不在 MVP 实现。

每个可发布条目的通用治理元数据预留可空的 `access_policy_ref`，MVP 保持为空，不纳入模型提取 schema，也不根据它执行权限判定。以后增加岗位/角色限制时，可在查询服务中统一执行，而不必改动甲乙双方的业务 schema。来源正文只在本企业资料治理入口按管理权限读取；普通详情返回获准展示的来源片段。未授权的条目 ID、关系路径和来源引用均不能越过企业边界。

业务 JSON API 和 MCP 都只暴露同一组只读语义：`search_ontology_items` 按词或自然语言返回当前已发布的条目摘要、ID、三级路径、范围与版本；`get_ontology_item` 按 ID 返回详情、一跳关系、范围、版本及来源片段。服务端先应用企业限制，再检索和计数。管理 API/命令负责提交来源、审核、发布及 schema 激活；外部 Agent 不直连 Fuseki。MCP 不暴露管理写操作。

## MVP 可视化编辑

企业工作区的画布只编辑**当前企业业务本体的知识条目、条目与既有分类节点的归属边及条目间关系**，不编辑三级分类树节点，也不编辑 LinkML 类、字段或 YAML/Python 文件。甲乙方各只能在自己的企业数据集内编辑当前试点二级品类。左侧显示分类与批次，中央显示服务端给出的当前已发布图局部视图及待审改动，右侧显示选中条目/关系的属性、适用范围、来源片段和模拟标记；不一次加载全企业所有图。平台管理员通过独立的平台入口修改通用本体，不进入企业画布。

MVP 支持在画布中新增、修改和移除业务知识条目及 schema 已允许的关系，并修改其可编辑属性。拖动连线后须选择关系类型；服务端检查主体/客体类型、企业归属、来源依据和当前本体版本。人工新增事实或关系必须绑定现有来源片段，或先保存审核人输入的陈述为新来源修订；缺少依据的改动只能留在待补证状态。当前 schema 无法表达的字段/关系交给缺口发现与 Git 审阅流程，画布不能绕过 `activate-schema`。

每次保存只提交变更操作和所见本体版本，不把整张图作为新真相源覆盖 Fuseki。服务端将操作加入企业待审批次，保留操作者、时间、来源和前后差异；“移除”仅影响下一发布版本，历史快照仍在。画布可预览已发布图与待审改动的差异，审核人与管理员沿用既定校验和发布流程。若编辑期间当前版本已变化，服务端拒绝旧版本提交并要求刷新、重新检查差异；普通查询在发布前始终只读旧的完整发布版。浏览器不能直接执行 SPARQL UPDATE。

三级分类树在单独菜单中用树形结构增删改节点及父子关系，固定只有 `采购负责类 → 一级品类 → 二级品类` 三层。企业管理员编辑本企业树，平台管理员编辑平台通用树；两种操作分别写入对应数据集的待审批次，经校验后发布新树版本。平台通用本体也经平台入口提交变更、校验并发布新版本。服务端校验树节点唯一父级、层级及引用关系；被已发布业务本体引用的节点不能直接删除，须先在新业务本体版本中处理引用。平台通用本体和通用树的新版本只用于之后新建企业的初始实例，现有企业本体和树不自动同步；现有企业如需采用新版通用内容，由本企业管理员审核并发布本企业的新版本。

## LangGraph Agent 与 Web 测试页

MVP 增加一个小型 LangGraph Agent，以本体只读工具进行搜索和详情读取，再根据工具返回内容生成回答。企业与二级品类在服务端固定为 `test_buyer1 / 电脑(台式机/笔记本)`，模型与浏览器都不能传入另一企业或品类。Agent 使用与 JSON API、MCP 相同的查询服务和授权范围，但不直接操作 Fuseki。Agent 不作采购条件判断或入围结论。

Web 测试页需本企业测试账号登录，只有提问框、答案、被引用的条目 ID、来源片段和本体版本。回答只能引用此次工具返回的已发布内容；检索无依据时明确说明未找到依据。该页面是本体问答的联调入口，不扩展为通用聊天平台；资料与候选治理在同一前端提供独立的最小管理页面。

## 本地部署与验证

本地试点让 Python 服务运行在 Windows 当前仓库环境，Fuseki/TDB2 运行在 Ubuntu WSL Docker 中。Fuseki 使用本项目独立配置、固定版本镜像与持久卷，只向本机服务开放；不改变已有容器、端口或卷。实施时先实测 Windows 到 WSL Fuseki 的连接与端口，再验证多企业独立数据集、重启和备份恢复。SQLite 文件与 Fuseki 数据卷都不提交 Git，备份步骤须覆盖两者。

MVP 验收按以下证据层次记录，不能以静态配置或服务健康检查冒充真实模型、浏览器或发布验证：

1. 甲乙两份模拟资料分别使用各自 schema 经**实际模型调用**自动提取；核对原文位置、模拟标记、项目范围及所用 schema 版本。无依据的模型建议不可直接发布。
2. 审核前普通查询不可见；甲乙各自审核并发布后，JSON API 与 MCP 可按 ID 和搜索读到本企业知识，跨企业 ID、关系及来源片段均不可读。乙方可查本企业成本与报价策略。
3. 用一段初版 schema 无法表达、但有原文依据的新增测试资料，验证自动发现缺口、起草 YAML、生成 Python；完成 Git 审阅、测试、部署后，激活前仍用旧版抽取，执行 `activate-schema` 后新任务使用新版。无效激活不得留下半更新的指针或审计。
4. 在真实 Fuseki/TDB2 故障注入与并发读取中证明发布原子性；失败时仍读完整旧版。新旧快照、来源、schema 版本与审计能在重启和恢复后核对。
5. 前端构建通过后，甲乙双方分别用本企业测试账号在浏览器打开图编辑页：查看已发布条目与待审覆盖层，新增或修改有来源的业务条目和关系、移除一个旧关系，检查差异和审计；画布不能修改三级树或 LinkML schema。发布前普通查询仍读旧版，发布后读新版。跨企业编辑、无来源发布、未知关系类型与过期版本提交必须失败。
6. 在独立的树形菜单中，企业管理员增删改本企业三级树节点并发布；平台管理员仅增删改平台通用树和通用本体。新建企业取得当时通用本体与通用树的独立实例；随后修改平台通用树或通用本体，已建企业的树和本体保持原版本。验证企业管理员只能看到和操作本企业，平台管理员不能进入企业本体或企业树的读写入口，删除已被本体引用的节点被拒绝。
7. 用甲方测试账号在浏览器打开 Agent 页面，提问笔记本知识并核对答案、条目 ID、来源与版本；询问无依据问题时显示无依据。另行验证 API、MCP 和 Agent 三个入口使用同一企业范围，并检查初始 Claude 参考风格在管理页、画布与问答页的一致性。
