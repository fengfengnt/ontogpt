# 采购对话草案分析 API/MCP 最小契约（设计稿）

状态：第二阶段产品接口规格，尚未实现；操作名和字段仅用于后续联调，不表示已冻结 HTTP 路径。第一阶段只交付[本体数据服务](../phase1-data-service-v0.md)。依据见[采购对话草案 API 决策](../issues/23-define-procurement-draft-api-contract.md)。

## 唯一对话判定操作

外部采购 Agent 每轮调用`analyze_procurement_draft`；MCP Tool 只适配同一 API。外部系统保存聊天、草案、采购员确认快照、审批与发布状态；本工程无对话会话状态，不返回“准许发布”。知识包和流程也可供有权限的查询 API 单独读取，但首版 Agent 完成一轮补问只需此判定操作。

| 请求内容 | 最小字段与含义 |
| --- | --- |
| 身份与追踪 | 经认证的当前甲方企业/用户或限定服务身份、`request_id`；请求体自报企业 ID 不赋予权限 |
| 原话 | 按时间排序的采购员原话、每段稳定 ID、发送人和时间；用于识别品类、提取值及定位新条件原文片段 |
| 当前草案 | 外部草案 ID/版本；已拆采购项、已选甲方二级品类、当前字段值及其来源、当前本次条件和必须/加分及评分信息；未确认项可为空 |
| 上轮版本 | 上轮甲方本体版本、分类树版本和已用知识包引用；用于列出变化及需重新确认项 |
| 确认快照 | 仅采购员确认整份需求与条件后提供：快照 ID/版本、确认人、确认时间和所有采购项；本工程核对其与原话的一致性 |

响应按采购项返回：完整三级品类候选及理由、分类状态，原话提取值及片段、已发布知识包字段/供应条件条目、LLM 发现的本次新要求、仅供选择的临时建议、适用企业硬约束、缺失/无效/需澄清项、流程候选或命中流程及步骤/职位、`READY`或`NOT_READY`、本轮版本与审计引用。返回的每条内容标明`PUBLISHED_KNOWLEDGE`、`EXTRACTED_FROM_USER_TEXT`或`LLM_SUGGESTION`，不能把临时内容伪装成已发布本体。

## 本次要求与知识包的边界

1. **品类**：从甲方最新已发布三级树判断。多个二级品类可能命中时返回候选，先请采购员选择，再确定采购项的知识包；大需求可拆为多项。
2. **有知识包**：返回分条的采集字段、供应条件模板与判定说明。原话明确表达且可定位片段、但知识包未收录的字段或条件，LLM 直接加入**本次草案要求**，标明原文位置和提取理由；无需逐条先点“采纳”。若原话含义不明，返回需澄清问题，不编造数量、门槛或分数。LLM 想推荐但原话未包含的内容只作为`LLM_SUGGESTION`，不能自行变成必填或必须项。
3. **无知识包**：返回`KNOWLEDGE_PACKAGE_MISSING`并给出 LLM 临时字段与条件建议；这些建议须由采购员逐项确认后才成为本次要求。已发布企业硬约束仍按范围适用，不因知识包缺失而失效。该品类知识包未发布的事实要在响应中明确显示；若临时要求已确认且其他校验通过，单纯缺知识包不阻止本次返回`READY`。
4. **本体候选**：原话提取的新要求和采购员采纳的临时建议先随外部草案流转；采购员确认整份条件快照后，本工程自动去重创建本企业待确认知识候选，保留原话、提取片段、确认人/时间、品类与项目范围。候选可用于本次采购，但在企业管理员发布前不作为后续采购的已发布知识。确认快照若与硬约束冲突，仍可留冲突候选供管理员审核，本次`NOT_READY`，不能发布为有效采购。
5. **适用规则与流程**：业务含义、硬约束冲突和企业审批流程命中由 LLM 判断；程序负责权限、必填字段、数据类型、引用版本及评分合计等基础校验。硬约束判断不确定时返回`NOT_READY`和需补问事项。预算等流程决定因素缺失、或多个流程可能命中时返回`FLOW_UNDETERMINED`、候选流程及缺失因素；流程可确定后返回已发布流程版本、步骤顺序、职位和判定理由，不执行审批。

## 版本与发布前复核

每轮读取**最新已发布**甲方本体与分类树，并比较上轮版本；规则或品类含义变化时列出受影响字段、条件与流程，要求采购员重新确认。外部系统正式发布前，必须带已确认条件快照再次调用本操作，按当时最新版复核原话与快照是否遗漏或矛盾；响应包括使用的版本、快照引用、逐项问题和`READY`/`NOT_READY`。原话没有的未采纳建议不阻止齐备；原话中已提但快照遗漏的要求使结果为`NOT_READY`。`READY`只表示本工程看到的数据齐备、规则未发现冲突且流程已可确定，不代替外部系统检查发布权限、实际审批及发布动作。若本体在复核后再次变化，外部系统应以发布时所采用的复核版本和快照绑定本次采购；后续在办事项沿该版本解释。

## 首轮示例（虚构字段）

以下展示最小请求与响应片段。`预算`是否必填完全取决于试点甲方已发布知识包；这里假设它必填，不能据此断言所有电脑采购都要填预算。

```json
{
  "request_id": "draft-check-1",
  "draft_ref": "external-draft-1",
  "utterances": [
    {"id": "u1", "sender_ref": "buyer-user-1", "sent_at": "2026-10-16T10:00:00+08:00", "text": "我要采购100台电脑"}
  ],
  "items": [],
  "previous_versions": null,
  "confirmed_snapshot": null
}
```

```json
{
  "request_id": "draft-check-1",
  "category_candidates": [
    {"path": ["IT与通讯", "办公设备", "电脑(台式机/笔记本)"], "status": "RESOLVED", "reason": "原话明确提出电脑采购"}
  ],
  "extracted_values": [
    {"field": "quantity", "value": 100, "unit": "台", "source_type": "EXTRACTED_FROM_USER_TEXT", "utterance_ref": "u1", "text_span": "100台电脑"}
  ],
  "knowledge_package": {"status": "PUBLISHED", "ref": "buyer-laptop-pack-v1"},
  "missing_fields": [{"field": "budget", "rule_ref": "buyer-budget-field-v1"}],
  "flow": {"status": "FLOW_UNDETERMINED", "missing_factors": ["budget"], "candidate_refs": ["buyer-flow-low-v1", "buyer-flow-high-v1"]},
  "hard_constraint_checks": [],
  "readiness": "NOT_READY",
  "versions": {"buyer_ontology": "buyer-v1", "buyer_tree": "buyer-tree-v1"},
  "audit_ref": "draft-audit-1"
}
```

采购员后续若说“必须五年维保”，LLM 可把有原话片段的该条件直接加入本次草案；如果它自行建议“最好另要三年驻场服务”，只能返回建议。外部 Agent 收集预算等必填值，请采购员确认**整份**条件快照，再按最新版复核。新维保条件在确认后自动入待确认本体候选；外部系统取得`READY`后仍自行办理审批和发布。
