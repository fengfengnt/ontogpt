# Agent 读取已发布企业本体：最小契约（设计稿）

状态：产品接口规格，尚未实现；操作名用于分阶段联调，HTTP 路径未冻结。第一阶段范围见[数据服务规格](../phase1-data-service-v0.md)，读取决策见[Agent 本体读取票据](../issues/27-define-agent-ontology-read-contract.md)。

## 普通读取：搜索后按 ID 取详情

第一阶段只提供`search_ontology_items`和`get_ontology_item`两个只读业务 API，MCP Tools 调用相同实现与权限检查。下表中的`assess_ontology_claim`留到第二阶段：

| 阶段与操作 | 最小输入 | 最小输出 |
| --- | --- | --- |
| 第一阶段 `search_ontology_items` | 自然语言或关键词、可选条目类型与品类范围、获授权的当前企业身份；跨企业时还需可核验采购关系与披露授权 | 已发布且有权可见的候选条目 ID、类型、简述、关联完整三级路径、当前本体/分类树版本、相关性说明及有限的相关关系路径 |
| 第一阶段 `get_ontology_item` | 搜索所得稳定条目 ID、可选搜索时观察到的版本、相同授权上下文 | 当前已发布条目详情、直接相邻关系的类型/方向及目标 ID/简述、适用范围与有效期、当前版本、获授权的来源原文片段及其来源引用/位置 |
| 第二阶段 `assess_ontology_claim` | 自然语言命题或问句、可选主体 ID/关系/客体/适用范围、获授权的当前企业身份 | `支持 / 反驳 / 依据不足 / 冲突`、解析出的命题与主体 ID、实际支持及反向路径、理由、来源与版本；歧义或缺少门槛时返回可披露的候选与缺失信息 |

普通搜索及按 ID 读取**只看当前最新已发布**的企业本体与分类树；不接受任意旧版编号作为普通查询目标。搜索结果仅表示语义相关，不能证明乙方拥有该能力或满足采购条件；统一业务判定属于第二阶段。候选、模型建议和未发布树节点不会伪装成已发布结果。

`get_ontology_item`只展开**一跳关系摘要**，不递归装载邻居的完整详情。带范围的业务事实按可引用的[RDF 陈述](../ontology/rdf-claim-provenance-v0.md)存储；一跳是业务关系的一跳，不将 `rdf:subject / rdf:predicate / rdf:object` 等存储字段计为多跳。面向问题的`search_ontology_items`先找相关条目，再按问题相关性沿有类型、有方向的已发布关系逐层扩展，首版最多三跳、最多返回十条相关路径；这两个数是试点初始上限，不是行业统一标准。路径携带实际节点/关系 ID、主体与目标类型、适用范围、来源引用和版本。关系遍历前先做权限过滤，不能由 LLM 补造不存在的边；无足够依据时明确返回证据不足。业务条件是否满足仍由专用判定 API 决定。[关联读取深度决策](../issues/28-define-ontology-retrieval-depth.md)说明理由与限制。

第二阶段的`assess_ontology_claim`复用上述授权检索和路径上限，对一个明确命题判断证据关系，不把搜索相关性或图上可达性直接当作证明。`支持`要求已发布证据在同一主体、关系含义、适用范围和有效期内支持命题；`反驳`要求明确相反的已发布事实；两者同时有效则为`冲突`，并分别返回路径。未找到明确依据、命题主体有歧义或已到检索上限仍无法判定，均为`依据不足`，同时返回缺失/歧义原因。LLM 可以判定文本与命题的语义关系，不能补造关系、改变路径主体或把“没查到”解释成否定。响应记录实际路径 ID、来源片段、判断理由、模型/提示词及检索版本，供外部 Agent 引用和排错。[结论与证据决策](../issues/29-define-ontology-answer-evidence-contract.md)说明四态含义。

调用方无需预先知道主体 ID。本工程从问句中解析主体、关系、客体和适用范围，并回显实际采用的命题与 ID；若多个有权可见的主体都可能对应“这家供应商”等指代，则返回`依据不足`及可披露的候选 ID/歧义说明。问“注册资本够吗”却没有门槛或单位、或关系含义不清时，也返回`依据不足`及缺失内容，不按猜测的含义判断。外部 Agent 自行决定是否补问。[自然语言命题转换决策](../issues/30-define-natural-language-claim-grounding.md)记录这一边界。

上述操作仅以获授权的最新版已发布内容为依据。本次采购的临时条件、乙方逐项声明及其与已发布事实的冲突，由第二阶段项目判定结合外部输入处理；其本次声明优先规则不改写通用核验结论。对“本次采购是否允许华硕”一类依赖外部采购条件的问题，若普通核验没有足以回答本次问题的已发布数据，返回`依据不足`和“缺少本次采购条件”的原因；可以另展示已发布通用规则，但不能据此给本次结论，也不指定外部 Agent 下一步调用或行动。

每个响应回显实际使用的本体和分类树版本。若搜索后新版本发布，按 ID 读取时发现调用方附带的观察版本已过期，返回版本变化提示，Agent 重新搜索或读取当前条目，不把两版内容悄悄拼在一起。若条目在最新版本已停用，不用普通读取回退到旧版。

## 来源与权限

条目详情可返回足以说明其来源的**授权原文片段**、来源 ID/修订、文件名和段落/字符位置；来源元数据本身也按权限裁剪。整份原始 Markdown 或自然语言材料只供本企业拥有资料权限的人通过资料管理功能查看，不作为普通 Agent 读取结果，也不提供整库下载。

检索范围先按调用身份、当前企业、业务动作及跨企业采购关系和披露授权限制，再生成搜索结果与计数。甲方只能发现乙方已发布且标为可供采购匹配的能力，以及对本次采购可披露的相关事实；乙方可在本企业权限内查询自身已发布内容。项目临时能力不属于普通已发布搜索，仍只随该项目的判定请求使用。未获授权时，按 ID 读取也不能借稳定 ID 绕过搜索范围。

## 历史解释与在办判定（第二阶段）

“普通查询只读最新版”不改变已启动事项的版本绑定。本工程在处理在办事项时，内部按该事项绑定的已发布快照判定；旧快照不可改。`explain_evaluation`由有权限的调用者通过**具体判定审计引用**查看当时记录的分类路径、规则、事实或本次声明片段、模型/阈值、版本及理由，并继续执行原采购关系与披露权限检查。它只解释该次判定，不提供按任意旧版本搜索完整企业本体的入口。

## 验收例（前 3 项属于第一阶段，其余属于第二阶段）

1. 采购 Agent 搜索“电脑采购”，先得到有权可见的二级品类与知识包 ID，再读取需求字段和供应条件；新候选尚未发布时，两步都看不到它。
2. 乙方 Agent 搜索本企业“笔记本五年维保”，能读到当前已发布能力及事实和授权来源片段；甲方无本次披露授权时搜索与按 ID 读取均看不到私有事实。
3. 搜索返回版本 V2 后发布 V3，带 V2 观察版本读取详情须提示版本变化；旧采购的审计说明仍引用其原判定中的 V2 内容，但普通搜索只返回 V3。
4. 核验“华硕是否在允许品牌范围”：有同一适用范围内的明确允许路径为`支持`，明确禁止路径为`反驳`，没有品牌范围事实为`依据不足`；两条有效路径互斥时为`冲突`，均返回可授权查看的来源。
5. 查询供应商五年维保时，品牌厂商的维保或注册资本不能作为该供应商事实；乙方针对本项目的“五年维保”声明不进入普通核验，但进入本次采购判定并与旧事实一起展示。
6. 问“这家供应商有五年维保吗”且上下文可见两家供应商时，返回`依据不足`和两家可披露候选 ID；问“华硕公司注册资本够吗”但没有金额门槛时，返回缺少门槛，不根据找到的注册资本直接判支持。
7. 问“本次采购是否允许华硕”且本工程只查到企业通用品牌规则时，返回`依据不足`并说明没有本次采购条件；外部 Agent 可据此回答“查不到”，无须按本工程指定的后续步骤行动。
