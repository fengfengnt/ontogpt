# 采购企业与供应商企业本体服务：产品与本体规格

状态：决策规格，待试点资料验证；不表示本仓库已有相应实现。决策来源见[产品决策地图](./map.md)及其子票据。

实施分期已确定：[第一阶段交付企业本体数据服务](./phase1-data-service-v0.md)，完成一甲一乙的资料提取、人工确认、版本发布及授权 API/MCP 读取；第二阶段交付采购草案、跨企业品类与条件判定及入围建议。下文描述**整体产品目标**；涉及判定的段落与接口均属于第二阶段。RDF/OWL 文件交换和授权只读 SPARQL 留待后期。

## 1. 产品目标与系统边界

分别为采购企业（甲方）和供应商企业（乙方）建立可确认、可发布、可追溯的企业本体库。本工程通过版本化 API 和 MCP Tools 向**外部**采购 Agent、供应商 Agent 提供本体查询、需求字段与流程判定、供应能力与准入条件判定。两类 Agent 使用同一核心语义，但只能读取其身份获准看到的企业视图。

本工程内部管理企业本体、分类树、候选确认、版本发布、供应能力、判定政策和判定审计。**外部业务系统**管理聊天、采购草案、采购需求发布与送达、乙方响应、材料披露、审批、正式入围、投标和合同记录。本工程的 `符合自动入围条件` 是判定结果，绝不是“已正式入围”的业务状态。

完整产品验收场景（第二阶段）：采购员说“我要采购 100 个电脑”；采购 Agent 调用本工程识别本企业品类，取得要填写的需求字段、供应商条件模板与审批流程，补问并请采购员确认；外部采购系统发布需求。供应商 Agent 从外部系统取得需求，调用本工程查询自身能力、补充材料并自检；甲方 Agent 用已披露证据重判。外部系统依据甲方审批或预授权政策记录入围并发送邀请。

首版先落地一家甲方和一家乙方；“行业”另行定义，不用它指代下述“采购负责类”。

## 2. 核心语义与数据归属

| 对象 | 最小含义与关系 | 权威归属 |
| --- | --- | --- |
| 企业本体版本 | 一家企业已发布的类、属性、关系、约束、职位、流程、规则和事实快照 | 本工程，按企业隔离 |
| 企业分类树版本 | 严格的 `采购负责类 → 一级品类 → 二级品类` 树；各非根节点只有一个父节点 | 本工程，甲乙方各持一棵树 |
| 二级品类知识包 | 甲方与二级品类关联的采集字段、供应条件模板、判定说明及解释文字的可引用条目集合；不是分类节点本身 | 甲方本体；本次取值与采购项在外部系统 |
| 企业约束规则 | 从企业资料提取并经确认发布、带适用范围和生效时间的硬约束；本次输入不得覆盖 | 甲方本体；知识包引用仅用于展示和追溯 |
| 采购需求采集字段 | 与甲方二级品类关联的必填性、类型、单位、范围、条件依赖及可用默认值 | 甲方本体；本次取值在外部系统 |
| 供应商条件模板 | 与甲方二级品类关联的可复用准入、证据和评分条件建议 | 甲方本体；本次门槛、权重与细则在外部系统确认 |
| 职位、任职与审批流程 | 本企业职位的职责、业务权限、任职人、上级职位和条件化审批步骤 | 甲方本体；审批实例在外部系统 |
| 供应能力 | 乙方可提供某个二级品类服务或物料的独立记录，关联独立的乙方事实，并带“可供采购匹配”标记 | 乙方本体；不是分类节点 |
| 自动入围政策 | 甲方确认发布的、允许机器结果用于自动邀请的适用规则 | 甲方本体；本次启用和授权记录在外部系统 |
| 采购项、乙方响应、正式入围 | 一次采购拆分项、乙方本次材料、甲方的最终邀请状态 | 外部业务系统；作为判定输入传入本工程 |
| 判定审计 | 输入引用、所用版本、逐项结果、模型/规则和理由 | 本工程；不是采购业务台账 |

甲乙方本体是同一核心语义的两种企业视图，均可有企业专属定义和实例。采购项引用甲方树中的二级品类；乙方能力引用乙方树中的二级品类。乙方可跨采购负责类和品类经营，但某个分类节点不跨父节点复用。品类归属不代表乙方具备其下所有能力。甲方一次需求可拆成多条完整三级路径，各采购项单独定义本次条件。

最小关系和约束如下，后续可据此落成正式的图谱 schema 与 API schema：

已发布事实与关系以**逐条可引用的陈述**为权威单位，保留主体、关系、客体或值、范围、有效期、来源和发布版本；图形化展示只是这些陈述的视图。同一事实可关联多份独立来源；带范围的事实不另写成无条件直接三元组。首版依据明确发布的关系做有界检索，由 LLM 结合知识包与本次输入判断业务含义，不承诺 OWL 形式逻辑推理。当前试点 Agent 接口是 JSON API/MCP。**Apache Jena TDB2 是首选本体权威存储，Fuseki 是访问服务**；从首版为企业、分类树、候选批次和不可变发布版本规划命名图，并给逐条陈述稳定 IRI。后期向授权系统开放只读 SPARQL，RDF/OWL 文件导入仍经候选确认，导出遵守已发布版本与披露权限。候选确认、冲突校验、版本切换和逐项授权由本工程实现。详见[修订后的存储决策](./issues/33-evaluate-jena-fuseki-as-authoritative-store.md)、[RDF 陈述与来源设计稿](./ontology/rdf-claim-provenance-v0.md)及[选型依据](./research/jena-fuseki-authoritative-store-v0.md)。

五种抽取承载结构中，`Class`是类定义，`Property`是字段或关系谓词定义，`Relation`是一次具体可引用陈述，`Constraint`是企业业务规则，`Instance`是具体对象。术语改名且含义不变时沿用 IRI；含义变化时新建 IRI。平台维护版本化的基础 SHACL 形状，对拟发布完整快照检查结构并阻止无效发布；企业可以扩展业务本体与规则，不能修改基础形状。采购条件和硬约束是否适用、是否满足仍由既定 LLM 判定处理。详见[RDF 词汇与 SHACL 设计稿](./ontology/rdf-vocabulary-shacl-v0.md)。

每家公司使用独立 TDB2 数据集，平台通用基线使用平台数据集；企业数据集内的候选、分类树和业务本体发布版本分图保存。当前读取视图只暴露获授权的最新版，历史和在办判定按绑定版本由内部服务读取。跨甲乙匹配由本工程分别读取两侧数据集并裁剪结果，不开放任意跨企业 SPARQL。详见[Jena 数据集与版本图布局](./ontology/jena-dataset-layout-v0.md)。

| 关系或约束 | 基数与判定 |
| --- | --- |
| 企业 → 已发布本体版本、已发布分类树版本 | 各有一条当前版本引用，历史版本可多条且不可改；两类版本独立 |
| 一级品类 → 采购负责类；二级品类 → 一级品类 | 各恰有一个父节点；分类树只有三级、无环，不跨树引用父节点 |
| 甲方二级品类 → 知识包 → 采集字段、供应商条件模板、判定说明 | 一对多；各条目有稳定 ID、来源并归入甲方本体版本，不直接等于本次采购条件 |
| 企业 → 企业约束规则 → 适用范围 | 一对多；已发布硬约束按范围生效，不因知识包漏写引用而失效；普通上级品类规则不隐式继承 |
| 乙方企业 → 供应能力 → 乙方二级品类 | 企业可有多条能力；每条能力引用一个叶节点及版本，记录可匹配标记与事实/证据 |
| 企业职位 → 任职人员、上级职位、业务权限 | 职位可多人任职；职位至多一个直接上级，审批步骤引用职位并记录实际操作人 |
| 外部采购需求 → 采购项 → 甲方二级品类 | 需求至少一个采购项；每项一条完整分类路径和本次独立条件集合；外部系统持有记录 |
| 判定结果 → 条件、证据、规则与版本 | 每个条件结果能回溯甲方规则、乙方事实或本次证据、两侧分类、本体及模型版本 |

类、属性、关系和约束既可来自通用基线，也可为企业专属定义；职位、人员、能力等是企业视图中的实例。一个公司是否同时担任采购方和供应方、物料与服务是否另有类型标记，不在首版假设中强加，待试点样本确认。

## 3. 本体建立、确认与版本

首次落地从企业自然语言概述生成业务本体**候选**。此时没有企业业务 schema，只用类、属性、关系、约束、实例五种通用结构承载提议；具体业务含义仍来自企业原文。三级品类节点和父子关系进入独立的分类树候选。有已确认的业务 schema 后，可从自然语言或 Markdown 按 schema 提取新候选，包括带适用范围与生效时间的企业硬约束。每个候选须能定位支持它的原文片段；找不到原文依据的 LLM 推断只列为模型建议，企业补充明确原话后才可提取为候选。资料新版保留旧来源与旧本体版本，明确变更产生带拟替代关系的候选，不自动覆盖旧内容；新版遗漏旧条目不代表撤销。详细契约见[企业资料投喂设计稿](./api/ontology-intake-v0.md)。

日常采购中本系统还会识别采购员**已确认**的新条件及乙方本次新声明，分别自动形成甲方、乙方待确认本体候选并去重，不要求外部 Agent 主动提交。候选不是已发布事实；新条件和乙方逐项声明可立即用于本次采购判定，但只有经各自企业确认发布后才成为本体内容。乙方可复用的能力和服务承诺发布后默认通用，原话或材料明确的项目、品牌、地域、品类与时间限制仍保留；本次项目来源始终可追溯。企业有确认权限的人逐项或批量采纳、拒绝；同一适用期的互斥候选须二选一，不同生效期的规则可并存。每项保留原文、发送人和时间，或文件名、原文片段、段落位置与文件版本；图上修改另记人工编辑来源。

每家企业同时最多有一个待发布业务本体批次。批次内候选须全部采纳或拒绝，暂缓项移出批次；有确认权限的人在图上保存修改，视为确认该修订并纳入批次。企业管理员查看差异，发布前完成引用完整性和事实冲突校验，整批发布为不可改快照。发布前，候选不作为**已发布企业本体**供新业务或 Agent 读取；采购员已确认的本次新条件和乙方本次声明仍作为该次判定的输入使用。企业分类树以独立批次、独立版本发布；已被引用的节点不物理删除，历史记录保留原路径和版本。

发布校验须检查候选引用的依赖闭包：依赖项已发布，或同一业务本体批次中已采纳；采纳一项不自动采纳它的依赖。若知识包或供应能力引用新分类节点，先发布包含该节点的企业分类树版本，再发布业务本体版本；两次发布之间如实返回知识包或能力暂缺。采纳拟替代旧规则的新候选时，审核人明确旧规则对新事项的终止生效时间及新规则开始生效时间；重叠冲突未解决不发布。旧快照及在办采购沿旧版解释。详见[企业候选审核与发布规则](./ontology/publication-rules-v0.md)。

平台通用业务本体基线与通用分类模板分别发布。首版可由一甲一乙两个试点经人工审核形成；以后同类业务中三家独立企业各有已确认相似内容，才进入新的通用候选审核。公开定义脱敏，受限后台保留来源。企业固定引用所采用版本，平台升级不自动覆盖企业；企业管理员预览差异、处理冲突并主动确认。企业本地定义不得悄悄改变通用术语原意。

对话草案由外部系统保存。本工程每一轮均按**当前最新已发布**的企业本体和分类树校验草案，并返回版本变化及受影响字段供重新确认。外部系统已启动的采购、竞标、履约及历史记录仍按启动时绑定的本体、分类和流程版本解释。

## 4. 甲方：一句话采购到数据齐备

1. 采购 Agent 传入采购员表述和已验证的当前企业身份。本工程返回采购负责类、一级品类、二级品类候选及理由；二级品类有歧义时返回`待确认`，由采购员选择。大需求可拆成多个采购项，各自选路径。
2. 对选定二级品类，读取甲方的知识包，返回可分别引用的采购需求采集字段、供应商条件模板及判定说明；同时查找适用的企业硬约束，知识包漏写引用也不能绕过约束。普通上级品类规则不隐式继承。值来源区分`原话提取`、`模板默认`、`采购员输入`和`LLM 建议`。LLM 从采购员原话定位出的新字段或条件直接加入本次草案要求，附原文片段；原话未提出的 LLM 建议不能自行成为必填或必须项。若该二级品类尚无已发布知识包，返回缺失状态与 LLM 临时字段/条件建议，采购员逐项确认后用于本次采购。Agent 按缺失或无效项补问；采购员确认整份需求取值、供应条件、必须项门槛和评分细则。本次已确认输入优先于模板默认建议，但不能覆盖企业已发布硬约束。模板默认值不会自动成为本次条件。
3. 外部 Agent 每轮发送当前草案和上轮本体/分类版本。本工程按最新版返回缺失项、无效项、条件依赖、受版本变化影响而需重确认的值。如果所选品类在新版停用或含义变化，返回品类待确认。
4. 本工程按已知金额等决定因素查询企业审批流程；缺因素时返回`流程待确定`及需补字段，齐备后返回命中的流程版本、步骤、职位与依据。同职位多人时，一人完成指定审批步骤即可，外部系统记录实际操作人。
5. 本工程对照采购员原话与外部系统传入的已确认条件快照，发现遗漏或矛盾时返回差异供重新确认；LLM 判定本次输入违反企业已发布硬约束时返回`规则冲突、需求数据未齐备`，无法确定是否冲突时也返回`需求数据未齐备/待澄清`。无冲突且已确定后，程序检查必填字段、数据类型、权限、规则版本、每采购项可计分条件满分合计 100、必须项最低通过分及单供应商采购的采购项汇总权重合计 100%。采购员确认整份快照后，本工程自动把其中新知识去重放入本企业待确认候选队列；有冲突的候选标明冲突，不能使本次需求变为齐备。外部系统正式发布前按最新本体与树再校验一次；发布权限、审批完成、发布动作与需求送达由外部系统负责。

示例：`100`可预填数量，但品牌、预算、电脑类型、维保、交期等由本企业该品类规则决定是否必填；未填或无效则返回具体问题。这里列举的字段是**示例**，试点企业已发布本体才是实际规则来源。

## 5. 乙方：自检、澄清与入围判定

外部采购系统把已发布需求授权送达乙方 Agent。乙方 Agent 传入需求及本次材料，可查询自身已发布且标为“可供采购匹配”的能力，独立自检可响应的采购项。若本次新声明一项尚未发布的供应能力，可用仅限本项目的临时完整三级路径作自检和甲方重判；新树节点与能力进入待确认队列，发布前不进入常规供应商检索。新能力发布时由乙方管理员明确确认检索开关。乙方自检只供乙方参考；甲方 Agent 取得乙方为**本次采购逐项授权披露**的证据或声明后重判，结果才可供甲方外部系统使用。第二阶段甲乙 Agent 可就准入条件缺口交换澄清、证据或承诺并重判；价格与合同条款谈判不在第二阶段范围内。[乙方本体结构设计稿](./ontology/supplier-model-v0.md)明确能力、事实与本次声明的关系。

判定分两层，不能互相替代。品类语义匹配只筛出可能供应该采购项的乙方；是否符合入围条件，须结合甲方该二级品类知识包、本次采购员给出的数量和预算等取值，以及乙方本体事实或本次证据逐项判断。采购电脑不应把只供应衣服的乙方送入后续条件判定。

- **品类覆盖**：比较甲乙双方完整三级路径各级名称、定义和说明。先由固定版本相似度模型给分，再由 LLM 判`等价/包含/不相关`。分数低于低阈值为`不匹配`；两阈值之间为`待判定`；达到高阈值后，仅`等价`为`匹配`，`包含`或无法判断仍为`待判定`。缺描述或模型失败也为`待判定`。仅`匹配`可进入自动入围条件。
- **具体条件**：所有采购与供应业务条件由 LLM 逐项判断，包括明确数值条件；程序只做基础结构与权限校验。LLM 可先找出与条件高相关的乙方本体内容、本次披露材料或乙方逐条件声明；高相关本身不等于满足。采购员本次新增、知识包尚未定义的条件，也由 LLM 直接判断；即使条件有主观成分，LLM 判满足也可进入预授权自动入围路径。资格预审按诚信申报处理：乙方针对该条件明确声明“有”即可作为本次满足依据，不强制上传证明文件；本次声明与已发布乙方事实相反时，以本次声明参与入围判定，同时标出冲突并形成待确认候选，不改写已发布本体。没有相关本体内容、材料或逐条件声明时为待补；无法判断时为待甲方核验。结构见[知识包本体设计稿](./ontology/knowledge-pack-v0.md)，接口与来源标记见[资格预审 API 契约](./api/prequalification-v0.md)。

每个采购项只按**本次判定阶段**适用的条件独立判断必须项与加分项；资格预审与投标后的方案符合性不能混为同一结论。“选择性满足项”按加分项处理。必须项可计分且可设最低通过分；计分必须项为 0 分必不通过，总分不能抵消失败的必须项。加分项待核验不阻止准入，但分数不能提前视为已得。单供应商采购要求乙方覆盖并通过**全部**采购项，最终比较时按各采购项权重汇总百分制得分；多供应商采购按项分别判断，不混排不同覆盖范围的总分。投标后的最终评分和供应商选定仍按甲方评审流程执行。

本工程返回逐项证据和四态汇总建议：

| 汇总状态 | 触发条件 | 外部 Agent 的表述 |
| --- | --- | --- |
| `不满足` | 必需品类明确不匹配，或任一必须项明确失败 | 指出失败项与依据 |
| `待乙方补资料` | 无明确失败，但缺少必要描述或证据 | 向乙方索取具体资料 |
| `待甲方核验` | 无明确失败或待补资料，但品类或某个条件仍无法判定，或自动授权缺失 | 交甲方业务流程处理 |
| `符合自动入围条件` | 全部必需品类高阈值等价，全部必须项机器通过，甲方政策和本次授权均有效 | 仅说“符合自动入围条件”；由外部系统告知是否已正式入围 |

甲方企业本体保存经确认发布的自动入围政策；外部系统对**本次采购显式启用**，传入可核验的授权记录、采购规则版本和入围截止时间。每个涉及的二级品类须已完成误入围案例的修正重测并由外部系统启用自动入围；单供应商多采购项时每项均须满足。只有政策适用、授权有效、所有必须项机器通过且无待补/待核验阻碍时，本工程才给出`符合自动入围条件`。外部系统可据此自动写入正式入围并发邀请；若不启用或授权无法核验，不能自动入围。自动动作记录执行服务身份、政策及授权版本，不冒充某位人员审批。

## 6. API 与 MCP 的最小契约

业务 API 是权威实现；MCP Tools 只适配同一 API，不另写读取、匹配、评分或授权逻辑。下表是**整体产品能力清单**，名称不是已冻结的 URL 或 JSON 字段；第一阶段仅开放“搜索已发布本体条目”和“按 ID 读取本体条目”，其余判定能力属于第二阶段：

| 能力 | 主要输入 | 最小输出 |
| --- | --- | --- |
| 搜索已发布本体条目 | 当前企业与权限、自然语言或关键词、可选条目类型/品类范围；跨企业另需采购关系与披露授权 | 当前最新版中有权可见的条目 ID、类型、简述、关联品类路径、版本及最多三跳的相关关系路径 |
| 按 ID 读取本体条目 | 稳定条目 ID、当前权限及可选的搜索观察版本 | 最新已发布条目详情与直接相邻的一跳关系摘要、适用范围、授权来源片段与位置、实际版本；版本变化时提示重新读取 |
| 核验明确本体命题 | 自然语言问句、可选主体 ID/关系/客体/适用范围、当前权限；跨企业另需采购关系及披露授权 | `支持 / 反驳 / 依据不足 / 冲突`、解析出的命题、真实支持/反向路径、来源、理由及版本；主体或门槛不明时返回可披露候选/缺失信息 |
| 识别采购品类 | 当前企业身份、自然语言需求 | 候选完整路径、歧义状态、理由、树版本 |
| 读取品类规则 | 已选二级品类、企业身份 | 需求字段、供应条件模板、默认值、来源和本体版本 |
| 分析与校验采购草案 | 采购员原话、已选品类、当前草案、上轮版本及可选的整份确认快照 | 品类候选、原话提取要求与临时建议、知识包缺失/条目、缺失/无效/需重确认项、适用硬约束、流程状态、数据齐备与版本变化；详见[采购草案 API 契约](./api/procurement-draft-v0.md) |
| 查询适用流程 | 企业身份、采购金额等决定因素 | 流程待确定或命中步骤、职位、规则版本与依据 |
| 查询可见供应能力 | 乙方身份或采购关系 | 可供匹配能力、对应分类路径与可披露字段 |
| 评估乙方响应 | 已确认的本次条件快照与采购员原话、外部采购项及规则版本、判定阶段、乙方逐条件声明与本次披露材料、截止时间、用途和授权引用 | 需求数据齐备或差异/硬约束冲突、品类三态、逐条件结果、声明或材料来源、四态汇总、自动生成的待确认候选引用、版本及审计引用 |
| 解释判定 | 判定审计引用和获授权身份 | 输入引用、模型/规则/阈值、证据、理由与版本 |

普通 Agent 搜索与按 ID 读取只看最新版，不能任意检索旧版本体；按 ID 读取返回一跳关系摘要，搜索按问题相关性沿有类型、有方向的真实关系最多扩展三跳、返回最多十条路径。此上限是试点初值，路径可达或文本相关不等于供应条件满足。第二阶段的明确命题核验接受自然语言问句和可选主体 ID，由本工程解析并回显命题，复用授权检索返回四态结论与路径；没找到明确事实、主体有歧义或缺少比较门槛时是`依据不足`，只有明确反向事实才是`反驳`，相同适用范围内正反事实并存是`冲突`。它不纳入本次采购声明；若本次条件缺失，返回不足及原因，不指定外部 Agent 的后续动作。本次声明与已发布事实的冲突由准入判定接口单独展示并按本次声明优先处理。整份企业原始资料不通过普通读取返回。第二阶段历史判定按绑定快照解释当时依据，仍受采购关系与披露权限限制。[Agent 本体读取设计稿](./api/ontology-read-v0.md)定义了读取与核验的版本变化处理。

乙方注册资本、成立日期、授权品牌、本地服务团队和过往案例等可复用资格与能力事实，由乙方确认后发布在其本体中。针对本采购项目的授权函等一次性材料，可由外部系统随请求传入可检索文本、来源与版本；原始 PDF/图片留在外部系统。乙方也可按条件逐项作诚信声明，记录原话、身份、时间及适用项目；入围判定可接受声明而无附件，返回依据类型为“乙方自述”，不称作已核验证明。完全没有相关本体内容、材料或逐项声明时为`待乙方补资料`，文本高相关但无实际满足判断不能直接通过。若已发布乙方事实与本次声明冲突，仍按本次声明判定并显式返回冲突，供外部系统及后续本体候选审核查看。[接口设计稿](./api/prequalification-v0.md)细化这些字段。

外部采购或乙方材料作为判定请求输入，本工程不保存聊天草案、采购需求、响应、原始附件和正式入围台账；可保留最小必要的判定审计。乙方自检请求与甲方采用的判定须标明用途，不能把乙方自检直接当作甲方正式决定。不确定判定由本工程明确返回并说明依据；外部系统负责后续处理和事后发现错误时的业务处置。API 不提供对外的采购发布、邀请、入围写入或供应商选定动作；MCP 不提供完整企业本体一次性下载资源。

交互式 Agent 沿用登录用户和当前企业权限；后台 Agent 使用绑定单一企业且明确授权的服务身份。服务端验证租户、业务动作、采购关系、乙方披露范围及自动入围授权，不能信任 Agent 自报的任意企业 ID 或未经核验的授权记录。甲方仅见本次可披露的乙方能力和证据；乙方仅见已向其开放的采购需求及自身结果。每次调用记录身份、企业、动作、外部请求标识、相关本体/分类/规则版本、时间和判定审计引用。

## 7. 试点验收场景

试点和回归案例先由人写下每个“采购项 × 乙方”的预期入围结论及理由，再运行本工程，由人对照判定与依据复核；这不是线上每笔采购的必经步骤。案例中的品类、证据可用 LLM 高阈值相关性筛选，具体事实仍按知识包规则核验。高相关证据返回有权可见的原文片段、来源、关联条件和理由。若本工程判可自动入围而人工预期不应入围，须修正知识包或判定规则并重测该案例，之后才对相应品类启用自动入围；不另设整体数值通过门槛。案例复核及启用状态由外部系统管理。

1. **需求形成**：输入“我要采购 100 个电脑”，返回正确或待确认的完整品类路径、已知数量、缺失字段和可用流程；采购员补齐后返回`数据齐备`，但接口不发布采购。
2. **歧义与版本**：同名不同父类、不同名同义及描述缺失分别得到可解释候选或待确认；对话期间发布新版时，下轮返回变化与需重确认项，不暗中沿用旧规则。
3. **多采购项**：电脑加工服拆为两项；单供应商须两项全覆盖，多供应商可分别响应。
4. **乙方自检和披露**：乙方未标记可匹配的能力不进入查找；自检不改变甲方结果；未授权披露的证据对甲方不可见。
5. **逐条件判定**：客观与主观业务条件均由 LLM 判断；乙方逐条件声明可诚信通过而无需原件；没有相关资料或声明为待补且截止后失败；任何必须项失败不因总分高而通过。企业硬约束无法判清时先补问，不继续自动入围。
6. **自动入围**：甲方企业政策已发布、涉及品类的案例复核已完成且已启用、本次已显式启用、授权可核验、品类高阈值等价且所有必须项经规则或 LLM 判满足时，本工程返回`符合自动入围条件`；正式入围和邀请仅在外部系统出现。关闭授权、停用品类自动入围或条件无法判断时不得返回该状态。
7. **隔离和追溯**：跨企业任意 ID 读取被拒绝；每次判定能重现所用路径、证据、模型、阈值、政策和版本；旧采购仍可按旧版本解释。
8. **阶段区分**：[模拟笔记本案例](./cases/PRO-IT-2026-014-review.md)中 S5 资格预审通过，后来因投标方案“送修”不满足“原厂上门 NBD”而废标；第二阶段入围判定不能将后者倒推为前者失败。该案例缺乙方逐项证据，仅用于建模和准备验收输入。
9. **企业硬约束**：已发布的餐标上限按适用范围生效，即使知识包未显式引用；采购员输入超过上限时 LLM 返回冲突及数据未齐备，无法确定是否超限时先补问，不返回自动入围。程序独立检查字段类型、权限和分数合计。
10. **知识包缺失与新要求**：二级品类缺知识包时，LLM 临时建议由采购员逐项确认后可用于本次；原话中可定位的新要求直接进入草案，原话没有的 LLM 推荐不自动变成要求；确认整份快照后新知识才进入待确认候选。发布前本体或分类升级时受影响项须重新确认。

## 8. 实施顺序与已知风险

第一阶段重点验证真实资料提取的来源准确性、图形编辑和批次发布的引用完整性，以及跨企业授权读取与备份恢复；以下 LLM 业务判定风险主要属于第二阶段。

1. **第一阶段：本体数据服务**：取得一家甲方和一家乙方授权材料，定义各自三级树、知识包、职位流程和供应能力；从自然语言/Markdown 生成候选，人工确认并发布分类树与企业本体版本；用授权 API/MCP 搜索和按 ID 读取，验证来源、版本与租户隔离。验收见[第一阶段范围](./phase1-data-service-v0.md)。
2. **第二阶段：统一判定服务**：在已发布本体之上实现采购草案校验、流程选择、跨企业品类匹配、乙方自检/甲方重判、逐条件解释和判定审计；通过外部 Agent 联调验证本工程只返回判定数据，外部系统负责采购和入围状态。
3. **后续复用与互操作**：由试点提炼通用基线与分类模板，再验证第二家企业采用与升级；按实际互操作需求交付 RDF/OWL 文件交换及授权只读 SPARQL。

**最大未验证风险**：用户选择让 LLM 判断全部业务条件和企业硬约束，包括数值比较；同时允许高阈值 LLM 品类匹配、乙方未经证明文件核验的逐项诚信声明参与自动正式邀请。声明甚至可与乙方旧本体事实冲突而仍通过本次入围判定。当前通过保留模型与规则版本、标明“乙方自述”、显示冲突、运行前人工写案例预期并复核结果、修正误入围案例后才启用品类自动入围来暴露和检验风险，但不设置整体数值通过门槛。未覆盖的场景仍可能误入围，数值条件也可能被 LLM 误判。阈值须在选定模型后、试运行前冻结。自由文本生成基础本体的质量、真实企业字段与图形编辑交互也须靠试点材料验证。OntoGPT 是否承担提取组件仍是技术选型问题，本规格不声称其已实现上述系统。
