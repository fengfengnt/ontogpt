# 第一阶段：企业本体数据服务范围与验收

状态：实施范围规格，待一家甲方和一家乙方的真实资料验证；不表示已有实现。整体目标见[产品规格](./product-spec.md)，阶段决策见[第 38 项](./issues/38-define-first-ontology-data-service-scope.md)。

## 交付边界

第一阶段把两家企业的资料变成**各自可确认、可发布、可授权读取的本体数据**。本工程负责企业隔离、资料来源、候选提取、人工确认、基础图形编辑、版本发布和查询；外部 Agent 负责使用返回的数据组织对话。查询结果只给条目、关系、规则原文与来源，不给“符合采购条件”或“可入围”的结论。

| 范围 | 第一阶段需要完成的能力 |
| --- | --- |
| 企业与权限 | 系统管理员建企业及企业管理员；企业授权人员维护本企业资料、分类树和本体；普通 Agent 按用户或绑定单一企业的服务身份访问，跨企业仅返回明确授权可披露的内容。 |
| 资料与候选 | 收自然语言或 Markdown；保留发送人/时间或文件版本/位置/原文片段；LLM 提议类、属性、关系、约束和实例，原文无依据的推断只列建议；重复语义候选可合并来源。 |
| 审核与发布 | 候选列表逐项或批量采纳/拒绝，冲突并列处理；同一企业本体一次只有一个待发布批次；基础图上编辑保存进入批次；依赖与同期冲突校验通过后由企业管理员发布不可改本体快照。分类树单独成批次发布，先发布新分类节点，再发布引用它的本体条目。 |
| 甲方数据 | 企业三级分类树；二级品类知识包中的需求采集字段、供应条件模板及说明；职位、任职、上级、流程定义和带适用范围的企业约束。每个条目有稳定 ID、来源、有效期和版本。 |
| 乙方数据 | 独立于分类节点的供应能力、可复用事实及其品牌/地域/品类等适用范围和有效期；能力发布时明确“可供采购匹配”标记。 |
| 对外读取 | 业务 JSON API `search_ontology_items` 和 `get_ontology_item`，以及调用同一实现的少量 MCP Tools；搜索返回相关条目和真实关系路径，按 ID 读取详情与一跳关联摘要。普通查询只看最新已发布版本，回显本体和分类树版本，并仅给授权的来源片段。 |
| 存储与恢复 | Apache Jena TDB2 为权威库，Fuseki 提供访问；每家公司独立数据集，命名图区分待审与不可改的发布版本。发布时完整校验并原子切换当前版本；提供数据集备份与恢复演练。RDF 内部表示不意味着第一阶段开放 RDF/OWL 文件交换或 SPARQL。 |

外部采购草案、采购需求、乙方本次响应、正式入围状态和原始附件仍保存在外部业务系统。平台通用业务基线和通用分类模板从试点提炼，第二家企业复用与升级属于后续扩展。

## 对外查询的含义

Agent 可先搜索“电脑采购”，取得本企业的完整三级路径、知识包和关联条目 ID，再逐个按 ID 读取字段定义、默认建议、规则原文与适用流程定义。乙方 Agent 可按本企业权限读取“供应笔记本电脑”的能力、事实和来源。搜索命中、路径相连或文字相似都**不代表**乙方满足甲方条件；第一阶段不输出业务四态结论。读取契约详见[Agent 本体读取设计稿](./api/ontology-read-v0.md)，其中 `assess_ontology_claim` 属于第二阶段。

## 验收场景

1. 用一家甲方和一家乙方的自然语言或 Markdown 生成候选；人工采纳后，发布两家的分类树和本体。未采纳、未发布的内容不会出现在普通 API/MCP 查询中。
2. 甲方查询“电脑采购”，读到本企业二级品类、知识包的待填字段与供应条件模板、适用流程**定义**及各条来源；乙方查询自身供应能力与事实。缺少知识包时如实返回缺失，不由读取接口临时编造规则。
3. 图上修改一个已发布条目后，普通查询仍读旧版；管理员发布新批次后读到新版。响应回显版本，旧快照不被覆盖。
4. 一家公司或 Agent 用另一家企业的条目 ID 直接读取，未获授权时不能取得内容或来源片段；乙方私有事实不能经搜索路径泄露给甲方。
5. 同一事实有两份独立来源时保留两条来源引用；改名不改义沿用 ID，改变含义生成新 ID。
6. 服务重启后，已发布版本、候选批次与来源引用仍可读；从备份恢复后，当前版本及历史快照保持一致，不出现只发布了一半的树或本体版本。

第二阶段再以“我要采购 100 个电脑”到甲乙 Agent 判定及外部正式邀请为端到端验收，接口草案见[采购草案](./api/procurement-draft-v0.md)和[资格预审](./api/prequalification-v0.md)。
