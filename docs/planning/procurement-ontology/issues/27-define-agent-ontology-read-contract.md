## Question

外部 Agent 除调用草案分析和入围判定，还应如何查找并读取其有权看到的**已发布**企业本体条目？查询怎样返回稳定对象引用、来源和版本，同时不把候选、供应商私有资料或完整企业本体误暴露？

## Established boundary

- API 是权威实现，MCP 只适配 API；首版 MCP 使用少量 Tools，不提供完整企业本体一次性下载 Resource。
- 交互式 Agent 继承用户及当前公司身份；后台 Agent 使用绑定单一企业的限定身份。跨企业读取须有采购关系和披露授权，不能凭请求体企业 ID 越权。
- 甲方知识包、流程、企业硬约束、乙方能力和事实均有稳定 ID、来源及已发布版本；未发布候选不作为 Agent 的企业事实。
- 外部业务系统拥有聊天、采购草案、需求发布和入围记录。本票只涉及本体**读取**，不新增确认、发布或业务写入能力。

## 用于检验选择的例子

采购 Agent 听到“我要采购 100 台电脑”，需要发现本企业相关二级品类及知识包，随后按 ID 读取字段和规则；供应商 Agent 要找本企业“笔记本电脑”能力及五年维保事实。两者事先都不知道条目 ID。

半年后审计员复查一笔旧采购，要按当时绑定的企业本体与分类树版本重现其品类路径和硬约束，不能因为新版改名而返回当前含义。甲方没有获乙方披露授权时，也不能借普通本体搜索读到乙方私有原文。

## Answer

- Agent 先按自然语言或关键词搜索已发布条目，获得 ID、类型、简述、关联品类路径和版本；再按 ID 读取详情。搜索相关性不等于供应条件满足。
- 普通 Agent 搜索和按 ID 读取**只看最新版**，不开放任意旧版本体搜索。响应回显实际版本；两步之间若发生发布，应提示版本变化，不静默混用新旧内容。
- 在办判定由本工程内部使用该事项绑定的旧快照；历史解释通过有权限的`explain_evaluation`按具体审计引用查看当时依据，而不是普通本体查询。这个范围解释保留了已确定的在办与历史版本规则。
- 条目详情返回按权限裁剪的来源原文片段、来源引用和位置；整份原始资料仅供本企业有资料权限的人读取，跨企业仍按本次披露授权限制。
- 两项普通读取操作、权限和验收例见[Agent 本体读取接口设计稿](../api/ontology-read-v0.md)。
