## Question

当前先实现“提供本体数据”的基础能力时，首版是否包含甲乙方品类匹配、逐条件判断和入围建议？若先只交付数据服务，甲乙方企业资料提取、候选审核、发布、分类树与知识包维护、授权查询和 API/MCP 的最小闭环如何界定，并怎样区分后续判定功能与后期 RDF/OWL 交换？

## Decision

分两阶段实施，当前先做**第一阶段：企业本体数据服务**。分别落地一家甲方和一家乙方，从自然语言或 Markdown 提取候选，人工确认，企业管理员发布不可改版本；维护企业三级分类树、甲方二级品类知识包、职位/流程/约束定义、乙方能力与事实及来源。外部 Agent 通过受权限控制的业务 JSON API/MCP 搜索已发布条目、按 ID 读取条目及关联摘要和来源片段。治理界面提供候选列表、批量确认与基础图形查看/编辑；编辑仍进入批次，发布后才对普通查询可见。分类树和本体分别发布。

第一阶段**不返回业务判定结论**：不做跨企业品类等价匹配、采购草案数据齐备/规则冲突判断、逐条件满足判断、通用命题四态核验或入围建议。搜索相关性和图上路径只帮助 Agent 找资料，不代表满足条件。外部 Agent 如需在此阶段自行解释资料，其结论不属于本工程的统一判定结果。本工程也不保存采购草案或正式入围记录。

**第二阶段：统一判定服务**复用同一已发布本体和权限边界，加入上述品类、流程、条件与入围建议的版本化可解释 API/MCP；外部系统继续管理对话、采购发布及正式入围。RDF/OWL 文件交换和授权只读 SPARQL 留待后期互操作阶段，不阻塞前两阶段；底层仍按已选的 Jena TDB2/Fuseki 方案建设。

第一阶段验收以一甲一乙试点为准：两家公司各能从资料形成候选并发布分类树和本体版本；甲方 Agent 能读取电脑品类知识包、字段和适用流程定义，乙方 Agent 能读取自身能力与事实；未发布内容、未授权的跨企业资料不可见；条目可追到授权原文和版本；修改发布后普通查询见新版，旧快照仍保留。此验收**不要求完成自动邀请入围**。
