## Question

为了让外部 Agent 从“采购 100 台电脑”取得必填字段、供应商条件和适用流程，并让本工程按已发布规则判定，每个二级品类知识包内部应怎样表示可引用、可编辑、可版本化的条目？企业级硬约束与本次采购确认的条件如何关联，而不把规则含义埋在一整段不可追溯的自然语言中？

## Current design boundary

- 三级分类树是索引，不直接承载采购条件；同一二级品类的知识包属于甲方企业本体版本。
- 知识包提供需求采集字段、供应商条件模板、材料或声明要求及判定规则；本次具体值与确认快照在外部系统。
- 本次新条件可先用于本次 LLM 判定，并自动成为待确认候选；发布后才成为可复用知识包规则。
- 甲方已发布硬约束不能被本次输入覆盖；乙方本次逐条件诚信声明可用于入围判断，即使与已发布乙方事实冲突，但须显示冲突。
- 本票只决定本体数据结构与规则边界，不选图库、规则引擎、OWL/SHACL 存储方式或实现代码。

## 第一轮选择

| 决策点 | 用户选择 | 影响 |
| --- | --- | --- |
| 知识包条目 | 分条建模并保留说明 | 每条可独立补问、引用与审计 |
| 企业硬约束 | 放入企业本体，作为可由投喂资料提取的约束规则 | 提取先成候选，确认发布后约束采购；适用范围细节待定 |
| 客观比较 | 所有条件都交 LLM 判断 | 不以结构化比较式驱动业务判断；基础格式校验边界待定 |
| 上级品类规则 | 显式引用，不隐式继承 | 下级知识包不会无意承接普通上级规则 |

例子：“采购 100 台电脑”首先命中甲方二级品类，知识包返回`数量`等采集字段、可选的供应条件建议，以及适用的企业硬约束引用。本次的`100 台`与采购员新写的“五年维保”仍在外部确认快照中；“五年维保”即使还不是知识包条目，也可据乙方本次逐项声明做判定，并自动进入甲方待确认候选。

## 已确认方向与待澄清边界

- 知识包分条建模，保留说明文字；每条可独立引用、溯源和随本体版本发布。
- 公司级硬约束可以成为**企业本体中的约束规则**。从企业投喂材料提取的规则先进入待确认候选，确认发布后才在适用范围内约束采购；这支持企业本体逐步丰富。
- 采购条件的业务判断**全部交给 LLM**；原建议“客观条件采用结构化比较式由规则引擎计算”未被采纳。接口基础结构校验仍用程序；LLM 对硬约束无法判断时返回需求数据未齐备并补问。
- 一级品类或采购负责类不向下级自动继承规则；可复用规则须显式引用。
- 企业级硬约束按本体中声明的适用范围直接生效，知识包引用只用于展示和追溯；上级品类的普通规则仍不隐式继承。

## Answer

- 形成[二级品类知识包与企业约束规则的最小本体结构](../ontology/knowledge-pack-v0.md)。知识包与二级品类关联，内部将需求采集字段、供应商条件模板、判定说明和解释文字分条建模；条目有稳定 ID、来源并随企业本体版本发布。分类树节点负责分类，不直接装本次条件；本次取值与确认快照由外部系统持有。
- 企业资料中的硬约束先作为**本企业本体候选**提取，企业确认发布后成为有适用范围、生效时间和原文来源的`EnterpriseConstraintRule`。它按范围直接生效，不依赖每个知识包都引用到它；知识包引用只供 Agent 展示与审计。本次采购员输入不能覆盖它。
- 所有**业务判断**交 LLM，包括客观数值条件、乙方条件满足、规则语义和硬约束冲突；不要求结构化比较式执行。程序仍验证必填字段、数据类型、权限、有效版本和分数合计。LLM 判断硬约束是否冲突不确定时，返回`需求数据未齐备/待澄清`，待采购员补充后重判，不继续自动入围。
- 采购负责类或一级品类上的普通条目不隐式继承到下级；知识包需要显式引用复用条目。企业硬约束的范围适用是独立机制，不受该“不继承”规则影响。
- 业务判断全部交 LLM 降低了数值规则的可重复性；审计必须保留规则原文、本次值、LLM 输出、理由、所用模型/提示配置版本。模拟案例的 9,500 元单价仍只是价格目标，本结构示例没有把它改为硬上限。
