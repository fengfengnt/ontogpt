## Question

最终企业本体与匹配结果供 Agent 使用时，哪些数据和判定应由权威业务服务通过版本化 API 提供，哪些适合作为 MCP Tools 或 Resources 暴露？如何沿用企业权限、来源证据、版本与审计边界，并避免 Agent 自行确认事实或决定入围？

## Answer

- 本工程的权威数据是已发布企业本体、分类树、职位与流程规则、乙方能力和本体版本；本次采购需求、乙方响应材料、人工审核结果及正式入围状态由外部业务系统管理。外部 Agent 经版本化 API 查询本体或提交本次数据请求判定；MCP 只是同一 API 的适配层，不复制判定或权限逻辑。首版 MCP 以少量 Tools 提供品类识别及应收集字段查询、适用流程查询、可见能力查询、供应商匹配与逐条件判定、依据读取；不提供一次性下载完整企业本体的 Resource。边界见[界定本体工程与外部 Agent 的业务边界](./14-define-ontology-service-agent-boundary.md)，本体发布见[第 13 项](./13-define-enterprise-ontology-publication.md)。
- 交互式 Agent 继承登录用户和当前公司身份；后台 Agent 使用绑定单一企业且授予明确业务权限的服务身份。业务 API 对每次调用校验身份、企业范围、业务动作及可见数据，MCP 不单独充当授权边界。调用审计至少记录调用身份、所属企业、操作、外部业务请求标识、本体对象及版本、时间与关联请求标识；匹配判定另保留[第 11 项](./11-define-category-semantic-matching.md)规定的必要输入、模型、阈值和理由。判定审计不等于本工程拥有采购或入围业务台账。
- 乙方仅将已确认且主动标为“可供采购匹配”的能力纳入候选查找。外部系统发布需求后可请求本工程按双方当时的三级分类路径和描述给出品类“匹配 / 不匹配 / 待判定”；只有“匹配”可供外部流程进入资格资料征集。若要求单一供应商，须对全部采购项均有匹配能力；允许多供应商时可按采购项分别征集。品类匹配不等于满足具体准入条件，也不等于正式入围。
- 乙方证据默认仅乙方可见。外部甲方系统向品类已判“匹配”的乙方征集资格资料；乙方通过外部业务流程响应，并对本次采购逐项授权披露证据。外部 Agent 将本次需求和已披露材料传给判定 API，本工程返回逐条件满足、缺失或待人工核验及依据；客观且可核验的必须项及其入围初评分可按已发布政策机器判定，主观项和争议证据仍交甲方授权人员确认。甲方预授权的自动入围条件见[第 16 项](./16-define-supplier-agent-shortlist-flow.md)。缺资料在入围截止前为“待补资料”，截止仍缺按不满足处理。乙方未授权披露的原文和完整本体不因能力可检索而开放。
- Agent 可在发布前查询采购品类的字段规则和适用流程，供采购员补齐本次需求；外部系统发布需求后，有相应权限的 Agent 才请求供应商匹配或明确重算。本工程不提供创建/发布采购需求、确认本体候选、写入正式入围或选定供应商的对外工具。甲方外部系统按企业职位、权限、流程及本次自动入围授权执行正式邀请并记录入围结论；本工程只返回可解释判定，不声称已正式入围。
- 甲方只看该采购可披露的乙方能力和证据，乙方只看向自己开放的甲方需求及自身判定结果。Agent 查询须按身份、当前企业和采购关系过滤，不能通过自报任意企业 ID 读取对方完整本体或来源原文；外部系统向乙方展示评标明细的时点沿用[第 10 项](./10-define-scoring.md)的规定。
