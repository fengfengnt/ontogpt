## Question

甲乙方首次只有企业介绍、采购或供货过程等自然语言与 Markdown，尚无本企业业务 schema 时，本工程如何把资料转为可逐项审核的定义和事实候选？同一来源改版、以及无法在原文定位的 LLM 推断，怎样避免静默改写已发布本体？

## Established boundary

- 首次落地从企业自然语言概述生成基础业务本体候选；有已确认的业务 schema 后再按 schema 提取。候选由人确认，管理员按单一待发布批次发布完整不可改企业本体版本。
- 每条候选记录来源原文或 Markdown 文件名、片段、位置、文件版本；自然语言另记发送人和时间。原始 Markdown 留在企业空间。
- 类、属性、关系、约束与企业实例可同时存在，但定义与实例不得混淆。甲乙方各自持有本体，分类树独立版本化。
- 同一生效期互斥内容在确认时并列显示；已发布内容不被自动覆盖。本工程可以内部自动去重产生候选，但候选不是事实。
- 本票只确定首次投喂与来源改版的产品契约，不选择抽取模型、数据库或页面实现。

## 用于检验选择的例子

甲方先输入“采购经理负责发布采购；超过 500 万元需采购经理、采购总监、CEO 审批”。系统应区分“采购经理”职位定义、其业务职责、审批流程或约束，并将每条候选指向原话。后来上传新版 Markdown，把阈值改为 800 万元；旧版流程已经发布且有在办采购引用。需要给审核人看出新旧差异，并决定新版是否替代旧版的后续适用期。

乙方输入“我们销售笔记本，并在上海提供五年维保”。系统应区分二级品类节点、供应能力、地域与服务承诺事实；若材料只写“服务很好”，不能凭模型补出明确 SLA 数值。

## Answer

- 首次没有本企业业务 schema 时，只用`Class`、`Property`、`Relation`、`Constraint`、`Instance`五种通用结构承载 LLM 提议；具体职位、流程、品类和能力含义从企业原文产生，仍逐项人工确认。三级分类节点及父子关系进入独立的分类树候选，不与业务本体版本混发。
- 同一 Markdown 或自然语言来源改版，保留旧来源和旧发布版本；新版提取为候选，若明确更改旧内容则关联`proposed_replaces`并显示差异，管理员发布后仅影响新事项。新版不再提到旧条目，不能自行解释为撤销。
- 无法在原文定位支持内容的 LLM 推断只作`MODEL_SUGGESTION`，不作为可确认事实候选；企业人员补充明确原话后重新提取。可定位原文的提议仍须确认和发布。
- 请求、输出、来源与验收例见[企业资料投喂接口设计稿](../api/ontology-intake-v0.md)。本票不选择具体抽取模型或存储引擎。
