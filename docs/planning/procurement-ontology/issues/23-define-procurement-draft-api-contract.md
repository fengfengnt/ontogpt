## Question

当采购员只说“我要采购 100 个电脑”并在多轮对话中补充条件时，外部 Agent 向本工程传什么、得到怎样的品类候选、待补字段、企业硬约束与流程判断、版本和数据齐备结果？知识包缺失或 LLM 提出新字段时，怎样保持本次可用且不把未确认内容冒充已发布本体？

## Established boundary

- 本工程不保存聊天和采购草案、不执行发布或审批；外部系统持有当前草案，每轮按企业最新已发布本体与分类树调用。
- 品类歧义由采购员选择；知识包分条返回字段和供应条件建议，原话提取值与模板默认值有来源，采购员确认后才成为本次条件。
- 所有业务条件、企业硬约束与流程适用判断交 LLM；程序负责权限、字段类型、版本引用和分数合计等基础校验。硬约束不确定时先补问。
- 采购员已确认的新条件可用于本次判定，并由本工程自动生成待确认本体候选；候选发布后才供后续采购复用。
- 外部系统需在正式发布前拥有可审计的本次条件快照；本工程只返回数据齐备和流程信息，不返回“有权发布”。

## 第一轮回答

- 二级品类尚无已发布知识包时，本工程可让 LLM 生成临时待填字段和条件建议；采购员逐项确认后可用于本次需求，并进入待确认本体知识。
- 知识包已有内容时，LLM 从采购员原话发现未收录的字段或条件，用户选择**直接设为本次要求**；第二轮明确须能定位原话片段，原话没有的推荐内容只作建议，整份快照确认后才入待确认本体候选。
- 审批流程适用性由 LLM 判断；缺少预算等决定因素或多个流程可能命中时，返回候选和所缺因素补问。
- 外部系统正式发布前，按最新已发布本体与分类树重新校验已确认条件快照；版本变化使字段/规则受影响时要求采购员重新确认。

## Answer

- 形成[采购对话草案分析 API/MCP 最小契约](../api/procurement-draft-v0.md)。外部 Agent 每轮向一个无会话状态的`analyze_procurement_draft`操作传采购员原话、当前草案、已选品类和上轮版本；本工程返回品类候选、来源明确的提取值、知识包条目、缺失/无效项、硬约束、流程状态、数据齐备与本轮版本。聊天、草案、确认快照、审批和发布仍由外部系统保存与执行。
- 若二级品类缺已发布知识包，明确返回缺失状态，LLM 可给临时字段和条件建议；**采购员逐项确认**后可用于本次采购，已发布硬约束仍按范围生效。若已有知识包，LLM 从采购员原话中**可定位具体片段**的新字段或条件可直接加入本次草案要求；原话没有、由 LLM 自行推荐的内容只作为建议，不能擅自变成必填或必须项。语义模糊处先补问，不编造门槛。
- 本次新知识在草案中标明原文、提取理由和“未发布”。采购员确认**整份**条件快照后，本工程自动去重写入本企业待确认候选队列；多轮未确认草案不入队。若确认内容与企业硬约束冲突，候选标明冲突供审核，但本次需求仍`NOT_READY`，不能借候选绕过约束。
- 已发布审批流程由 LLM 按本次已填因素判断适用性；预算等因素缺失或多个流程可能命中时返回`FLOW_UNDETERMINED`、候选及所缺字段，由 Agent 补问，不选最可能流程。流程确定后返回步骤、职位、版本和理由，不执行审批。
- 每轮使用最新已发布本体与分类树；外部系统正式发布前携带已确认快照再校验。版本变化导致的品类、字段、条件和流程差异须返回并由采购员重新确认。`READY`仅为数据齐备，不是发布权限或审批完成。外部系统绑定本次正式发布时采用的本体、分类与流程版本，供在办和历史解释。
