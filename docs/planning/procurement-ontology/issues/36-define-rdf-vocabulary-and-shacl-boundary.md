## Question

首版如何为类、属性、关系、约束、实例，以及带范围的事实陈述确定稳定词汇与 IRI？哪些结构完整性、引用、数据类型和范围要求由 SHACL 在发布前验证，哪些采购业务条件仍交给已发布知识包与 LLM 判定？

## Decision

- 五种结构是**抽取候选的类型**，不是五种互不相关的数据库表。`Class`定义一类对象；`Property`定义可用于字段或对象连接的谓词；`Relation`是具体主体使用该谓词形成的可引用陈述；`Constraint`是带范围、来源和有效期的企业业务规则；`Instance`是具体对象。RDF/OWL 映射见[词汇与校验设计稿](../ontology/rdf-vocabulary-shacl-v0.md)。三级品类节点及父子关系仍归独立分类树版本。
- 已发布术语使用稳定 IRI，名称和说明性文字更新而**含义不变**时沿用 IRI；主体类型、谓词含义或适用含义改变时新建 IRI，旧 IRI 留在历史版本。候选 ID 与已发布术语 IRI 分开。采用的通用基线术语保留基线 IRI，企业专属定义使用该企业命名空间。
- 首版基础 SHACL 形状由平台维护并版本化，企业不能编辑它。发布前对拟发布的完整快照验证必需字段、节点种类、数量、来源引用及已表达的范围/时间格式；不通过时给出具体条目和字段并阻止发布。跨数据集引用、权限、树的先后发布、冲突与事务由本工程程序继续校验。
- “餐标不得超过 200 元/人”等企业规则是可进化的**业务约束资源**，不转成首版 SHACL 上限或 OWL 自动推理规则。SHACL 仅检验它是否有可发布的结构；条件适用性和是否被本次采购违反仍按已定 LLM 判定及缺信息补问规则处理。
- 生产环境的 HTTPS IRI 根须在首次对外发布 RDF 前绑定平台可长期控制的域名；此规格只固定命名原则，不虚构实际域名。更换域名会影响外部引用，不能把它当作普通标签改名。
