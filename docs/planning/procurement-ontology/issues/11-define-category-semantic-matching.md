# 界定跨企业品类语义匹配的判定与验收

Type: grilling
Status: resolved
Blocked by: 08, 07

## Related

- [界定分类树的来源与维护责任](./08-define-taxonomy-source.md)
- [界定可解释匹配的判定与结果](./07-define-explainable-matching.md)

## Question

甲乙方各有分类树时，系统如何以完整三级路径及描述给出“匹配 / 不匹配 / 待判定”结果？规则或模型、判定阈值和重算时机如何确定；怎样用试点正反例衡量误匹配与漏匹配、设定首版验收门槛，并使每次判定及所用版本可审计？

## Answer

- 只有语义等价的二级品类才可自动判“匹配”。乙方的宽泛服务可能包含甲方具体需求时判“待判定”，不据此入围；乙方可补充明确的对应二级品类能力。比较甲乙方完整三级路径各级的名称、定义和说明；必要描述缺失时提示补充并判“待判定”。
- 首版先由固定版本的文本相似度模型给出分数，再由 LLM 区分“等价 / 包含 / 不相关”。选定具体相似度模型后、试运行开始前设定并冻结两个数值阈值，要求低阈值小于高阈值；当前不在未知评分尺度上写死数字。分数低于低阈值判“不匹配”，大于或等于低阈值但低于高阈值判“待判定”；达到高阈值后，仅 LLM 判“等价”才为“匹配”，判“包含”或无法判断为“待判定”，判“不相关”为“不匹配”。缺描述或模型失败也判“待判定”。后续修改模型、提示词或阈值须发布新判定版本。
- 甲方正式寻找乙方的匹配仅在外部系统发布采购需求并发起查找，或甲方对该需求明确重算时计算；乙方修改分类树本身不触发跨企业匹配。乙方 Agent 收到外部系统送达的需求后可独立发起**自检**，但不改变甲方既有结果或外部入围状态，见[供应商 Agent 准入契约](./16-define-supplier-agent-shortlist-flow.md)。每次计算使用传入需求及当时的乙方能力、双方分类版本；重算生成新审计结果，旧结果留档。补充描述和能力后，须等新请求才使用新内容。
- 每次判定保留采购需求与采购项、乙方能力、双方分类节点及版本、比较文本、相似度模型和分数、高低阈值、LLM 模型与提示词版本、关系判断、三态结果、简要理由、触发人或事件及时间，供逐项解释和有权限的专家审计。品类匹配自动完成；具体必须项按[界定可解释匹配的判定与结果](./07-define-explainable-matching.md)分别由机器判定或甲方审核人核验。
- 首版试运行案例和参考标签均由**线上同一 LLM**生成，不做专家人工标注。记录各三态数量及比例、包含/缺描述/模型失败数量、与该 LLM 参考标签的一致与分歧，不设通过门槛。这些统计属于自一致性观察，不能作为独立业务真值、真实误匹配率或已达到质量验收标准的证明。
- 用户在[供应商 Agent 准入契约](./16-define-supplier-agent-shortlist-flow.md)中选择：达到冻结的高阈值且 LLM 判“等价”的品类结果可进入甲方预授权的自动入围路径，仍须所有必须项机器通过。由于本项没有独立业务标注与误匹配率验收，自动邀请的误匹配风险尚未量化，应保留模型、输入、阈值和依据供追溯。
- 后续[界定二级品类知识包与案例验收](./17-define-category-knowledge-pack-and-case-review.md)补充了**最终入围结果**的试点与回归案例人工预期、复核和误入围案例修正重测要求；本项所说“无专家标注”特指品类等价的独立标注和量化误匹配率，不能否定后续的结果案例复核。
- **本体候选**逐项人工确认、全部确认后以企业本体新版本发布的具体流程由[界定企业本体版本的确认与发布](./13-define-enterprise-ontology-publication.md)决定；Agent 如何经 API 或 MCP 获取本体与匹配结果由[界定 Agent 访问企业本体与匹配结果的接口](./12-define-agent-ontology-interface.md)决定。
